## 1. هل يمكن تسجيل دخول Google إنتاجي غير مراقب؟

**لا، غير ممكن تقنياً.** وهذا ليس رأياً بل قيد في البنية:

| النقطة | الدليل الفعلي |
|---|---|
| المتصفح الآلي لا يرث جلسة متصفح آخر | `chrome-devtools-mcp` مُهيَّأ بلا `browserUrl` ولا `userDataDir`، فهو يفتح ملفاً خاصاً به. الفحص على `velnix-6c1a2.web.app` أعاد `hasPersistedSession: false` و`currentUserPresent: false` |
| لا يوجد منفذ debugging في متصفح المالك | `lsof` على منافذ CDP (`9222/9223`) ⇒ لا نتيجة. متصفح Chrome يعمل لكنه **غير قابل للربط خارجياً** |
| Google نفسها تُصنِّف المتصفح الآلي | `signInWithPopup` يفتح نافذة Google؛ أي حقن أو إكمال آلي فيها = تجاوز لحماية Google، وهو ممنوع في هذا المشروع |

**الخلاصة:** لا يوجد أي مسار يصل إلى تسجيل دخول إنتاجي بلا تدخّل بشري واحد. أي ادّعاء بغير ذلك غير صحيح.

## 2. آلية الأتمتة المدعومة المتوفرة

| البيئة | الآلية | غير مراقب | مصادقة Google | App Check | قواعد Firestore |
|---|---|---|---|---|---|
| **المحاكي** | Playwright 1.64 + Chromium على `flutter build web` | ✅ نعم | اصطناعية (Auth Emulator) | CustomProvider محلي | **قواعد الإنتاج نفسها** |
| **الإنتاج** | Playwright `connectOverCDP` على متصفح المالك | ⚠️ بعد خطوة بشرية واحدة | Google الحقيقية | **الحقيقية** | **الحقيقية** |

### 2.1 المحاكي — أتمتة كاملة بلا مراقب ✅
البنية القائمة في `scripts/emulator-preview/` تُشغّل **تطبيق Velnix الحقيقي**:
`lib/live/` كاملة + Functions الحقيقية + قواعد Firestore الحقيقية + سياسة الصلاحيات الحقيقية.
الشيء الوحيد الاصطناعي هو **مزوّد الهوية**، لأن Auth Emulator يقوم مقام Google — فلا يُلمس أي حساب Google ولا كوكي ولا توكن.

> `main.dart` المُستبدَل اصطناعي عمداً، وهو **يرفض أي مصدر غير loopback**، فيستحيل أن يلمس الإنتاج.

### 2.2 الإنتاج — الخطوة البشرية الواحدة
الربط بسجل Google القائم يتم عبر **CDP الرسمي** (نفس الآلية التي يستخدمها Chrome DevTools وPlaywright وPuppeteer — واجهة رسمية مدعومة، وليست تجاوزاً):

```bash
# خطوة واحدة: إغلاق Chrome ثم تشغيله بمنفذ debug
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --remote-debugging-port=9222 --user-data-dir="$HOME/Library/Application Support/Google/Chrome"
```
ثم: تسجيل الدخول مرة واحدة إلى `velnix-6c1a2.web.app` ⇒ ثم يصبح كل شيء آلياً بالكامل.

**لماذا لا يمكن حذف هذه الخطوة؟** لأن جلسة Google تعيش في ملف تعريف المتصفح المالك ومشفّرة بمفتاح نظامه؛ استخراجها أو نقلها أو نسخها **ممنوع صراحةً**، وإلا فهو تجاوز لحماية Google. ولا يمكن لمتصفح آلي أن يصل إليها منفرداً لأن Google لا تكشف الجلسة لعميل CDP جديد بلا منفذ debugging مفعّل مسبقاً.

## 3. ماذا جرى في المحاكي فعلياً

`scripts/emulator-preview/stage3-acceptance.cjs` — **11/11 سيناريو ناجح**:

| # | السيناريو | الأثر |
|---|---|---|
| 1 | لوحة المدير العام تظهر بعد المصادقة | جلسة داخلية صالحة |
| 2 | إنشاء طلب اصطناعي واحد عبر **نموذج UI الحقيقي** | الوسم المعتمد، هاتف `0000000000`، كمية `1`، مبلغ `0` |
| 3 | الحمولة تطابق الـfixture المعتمد بالضبط | `companyId=null` و`trackingNumber=null` |
| 4 | إعادة إرسال الحمولة نفسها ⇒ **لا طلب ثانٍ** | `requestKey` المُولَّد من الواجهة يحمي من التكرار |
| 5 | تعديل الملاحظات عبر UI + تقدّم `revision` | `1 → 2` |
| 6 | البحث بالوسم المعتمد ⇒ نتيجة واحدة | استعلام UI حقيقي |
| 7 | أربعة تحويلات داخلية + نافذة تأكيد الإكمال | `delivered` + `completionSource=internal` + قفل التعديل |
| 8 | الإشعار الداخلي يُعرض ويُقرأ | إثبات القراءة |
| 9 | دور غير مخوّل لا يستطيع التعديل ولا الإكمال | `permission-denied` |
| 10 | **المُحقِّق المستقل يقبل الرحلة المنتَجة من الواجهة** | `decision: PASS` — `14/14` بوابة إلزامية |
| 11 | لا مورد إنتاجي مساس + لا خطأ صفحة | نطاق محلي بالكامل |

### 3.1 إثبات مهم: `requestKey` ليس الوسم
اكتُشف بالقياس المباشر من الواجهة:
- `_requestKey` = `Random.secure()` ⇒ **30 محرفاً عشوائياً لكل نموذج**، وليس الوسم.
- الحماية من التكرار تعتمد على **ثبات المفتاح داخل النموذج الواحد**؛ إعادة فتح النموذج تُنتج مفتاحاً جديداً ⇒ احتمال طلب ثانٍ.
- لذلك فحص `B1` **بالوسم** هو شبكة الأمان الحقيقية، وقد صار الآن `FAIL` صارماً عند التكرار.

### 3.2 النتيجة النهائية الموحّدة

 "decision":"PASS","mandatoryPassed":"14/14",

## 4. تصحيح التقارير في `stage3_partb_verify.js`

| # | المشكلة | المعالجة |
|---|---|---|
| 1 | كل البوابات `NOT TESTED` ⇒ قرار `PASS` | القرار `PASS` ممكن فقط إذا اجتازت **كل** البوابة الإلزامية؛ وإلا `NOT_EXECUTED` |
| 2 | `NOT TESTED` قد يتصاعد صامتاً | `NOT_EXECUTED` و`UNVERIFIED` لا يمكنهما إنتاج `PASS` أبداً |
| 3 | فشل بوابة مُختبَرة مغطّى بنقص بوابات أخرى | ترتيب الأولوية: **فشل قاطع يتقدّم على النقص** — التكرار يبقى `FAIL` |
| 4 | `B2` كان عدّاً بلا هوية | `B2r` إلزامي: سجلّ التكرار يجب أن يشير إلى **هذا** الطلب بالضبط |
| 5 | قراءة ناقصة أو صفحة غير مكتملة | اجعل القرار `UNVERIFIED` |
| 6 | خلط الأدلة | كل صف يحمل `source: frontend\|backend` |
| 7 | `A3` كان `users.length === 1` ولا يفحص `emailVerified` | **تصحيحان في واحد**: لا يوجد «مستخدم واحد» كخاصية أمنية (يُفشل أي مؤسسة بأكثر من موظف)، والآن يجب **تمكين + توثيق + مرتبط بـgoogle** |

## 5. ما الذي تبقّى قبل التنفيذ على الإنتاج

1. **موافقة صريحة** على التنفيذ (لا يمكن لأداة آلية منح نفسها هذا الإذن).
2. **الخطوة البشرية الواحدة**: تشغيل المتصفح بمنفذ `9222` وتسجيل الدخول مرة واحدة.
3. التحقق من عدم وجود الوسم مسبقاً: `B1 ⇒ 0 tagged`.
4. تشغيل الرحلة الآلية عبر `connectOverCDP`.
5. **على أي حفظ غامض: إيقاف وفحص الخادم — لا تُعِد فتح النموذج إطلاقاً.**
6. تشغيل `node functions/scripts/stage3_partb_verify.js` وإرفاق نتيجته.

### 5.1 ما لن يُنفَّذ آلياً أبداً — بصراحة
- **`F1` منع Firestore المباشر**: لا يُرى إلا من جلسة المتصفح نفسها. يبقى `NOT TESTED` ما لم يؤكده المالك بنفسه. **لن أدّعي PASS لشيٍّ لم أره.**

## 6. ضمانات السلامة المُطبَّقة

| الضمان | كيف |
|---|---|
| لا تجاوز لـGoogle | لا حقن ولا استخراج كوكي ولا توكن ولا كلمة مرور |
| لا تعطيل App Check | لا تغيير في أي إعداد؛ الإنتاج يبقى على `reCAPTCHA v3` |
| لا تخفيف لقواعد Firestore | القواعد نفسها مستخدمة في الإنتاج والمحاكي |
| لا مدير إنتاجي إضافي | `joinRequests` و`members` لم يُمَسّا |
| لا كتابة بديلة من الخادم | الرحلة كلّها عبر UI؛ الأدوات الخلفية **قراءة فقط** |
| لا نشر | لم يُعدَّل أي مورد ولا Hosting |
| نطاق الإنتاج | تحقق `curl 200` + `decision: NOT_EXECUTED` + `orderId: None` |
