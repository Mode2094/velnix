# إكمال تشغيل Firebase — المرحلة الأولى بعد تأسيس المدير

المصدر الأساسي: bfef132 على audit/production-readiness. أكد المالك نجاح توثيق Google وإنشاء generalManager للحساب المعتمد مع readbackVerified=true وإزالة نطاق Cloud Shell المؤقت. هذه أدلة المالك وليست قراءة جديدة من Codex. تأسيس الإدارة **مغلق ولا يعاد**. إجراء هذه المهمة لا يستورد bootstrap ولا ينشئ أو يغير عضوية أو Auth أو مورداً سحابياً.

## ما أُنجز برمجياً

أضيف operational_readiness.js وإجراء Cloud Shell واحد يستخدم جلسة gcloud البشرية للحساب المخول؛ لا ADC أو Service Account JSON. يقرأ بالـGET APIs الرسمية فقط، باستثناء Admin Auth getUser (عملية قراءة) وgcloud projects get-iam-policy (قراءة). لا تسجيل Google جديد أو إضافة نطاق مؤقت أو Web Preview مطلوب لهذا الجرد. Authorization وquota header يظلان داخل العملية؛ لا أجسام أخطاء أو أسرار أو device tokens أو أسماء موظفين في التقرير.

يقرأ المشروع والخطة المالية من billingInfo، مزود Google والنطاقات، العضوية الحالية والقفل وسجل Auth للـUID نفسه، قاعدة Firestore وموقعها، القواعد المنشورة ويقارن تجزئتها بالمصدر، جاهزية كل واحد من 109 فهارس، الدوال المتاحة في europe-west1 وهوية تشغيلها وحالتها، التسجيلات الثلاثة المعتمدة وSDK/OAuth وشهادات Android، تسجيل App Check وenforcement وAPIs المفعلة، bindings هوية التشغيل في IAM على مستوى المشروع، ووجود مفاتيح KMS في europe-west1 فقط. يقرأ شركات التوصيل بترشيح provider/enabled فقط لكشف خطر تشغيل scheduler على إعدادات قديمة، دون قراءة اعتماداتها أو بيانات الطلبات أو الاتصال بها.

الفشل أو 403 أو الرد غير المتوقع أو pagination المتكرر يبقى unverified؛ لا يعني خلو الخدمة. read يعني وصول القراءة إلى API، وليس نجاح رحلة حقيقية. لا إثبات لمصدر Backend المنشور من الاسم والحالة؛ يلزم نشر نسخة مخولة موثقة أو مراجعة provenance. IAM الموروث وشروط المنح وسياسة كل KMS key ليست مثبتة بجرد project bindings. KMS خارج europe-west1 غير مفحوص. قراءة App Check ليست إثبات attestation أو رفض callable الحقيقي.

## نطاق النشر الجاهز للمراجعة — غير مفوض

Manifest المصدر يحصر 32 دالة: 28 callable، وHTTP webhook واحدة، وschedule واحدة، وFirestore triggers اثنتان. Functions تستخدم Node22 وeurope-west1، وcallables enforceAppCheck=true. sourcePlan يحصي جميع exports ويتوقف إن ظهر تعريف لا يستطيع تصنيفه؛ يمكن فحصه محلياً دون Google. القواعد deny-by-default وتسمح فقط بقراءة العضو وقرار انضمامه لنفسه؛ الكتابة والطلبات والإدارة عبر Backend. لا تغيير في صلاحيات الأعمال أو دورة الطلب أو كود المحول.

قبل النشر:

1. راجع نتيجة الجرد وSHA وPush/PR CI والدوال القديمة إن وجدت. لا تستنتج أن قاعدة البيانات خالية. وثق وضع الأعضاء الحالي مع المحافظة على المدير وAudit.
2. اعتمد runtime service account موجوداً في المشروع بعد مراجعة IAM الفعلية. تحتاج العمليات الحالية Firestore، قراءة وتحديث Auth وسحب sessions، وFCM عند الإشعارات. أمثلة IAM مراجعة فقط؛ لا تستبدل policy أو تمنح Owner/Editor تلقائياً. مفاتيح إدارة خاصة ليست مطلوبة.
3. ملف functions/.env.<project> محلي مستثنى: هوية تشغيل معتمدة، ALLOWED_DELIVERY_HOSTS فارغ، KMS فارغ للطلبات الداخلية. أزيل placeholder غير صالح للمشروع من المثال؛ لا إنشاء KMS بلا حاجة. Click يظل محجوباً ولا يستبدل بـgeneric_v1. أي شركة قديمة enabled تحتاج قراراً قبل نشر scheduler.
4. ثبت النسخة المعتمدة ومصدر البناء وتجزئات القواعد والفهارس. احتفظ بنسخة محلية آمنة من **القواعد المنشورة الحالية** والفهارس ومراجع إصدارات Functions/Cloud Run وإعداداتها غير السرية قبل التغيير؛ تجزئة المصدر وحدها ليست backup. حدد آخر إصدار آمن فعلياً؛ لا تختلق إصدار تراجع إن لم يوجد نشر سابق.
5. بعد الموافقة المحددة فقط: نشر القواعد والفهارس وFunctions بإعداد المشروع الصريح، دون force أو حذف دوال قديمة غير مراجعة، ثم انتظار READY والتحقق من regions وهوية كل خدمة وApp Check وCloud Run invocation. لا يوجد deploy تلقائي في الأدوات الجديدة.
6. تحقق من مواقع Firestore/Functions/Eventarc من الجرد؛ لا تفترض أنها متطابقة ولا تنقل القاعدة. وجود eur3 مثلاً لا يساوي تلقائياً فشل توافق europe-west1؛ يلزم اختيار trigger location الموافق للقاعدة وفق دعم Firebase الفعلي. Auth وApp Check وFCM خدمات project/global؛ KMS إقليمي ويخص الاعتمادات المؤجلة.

مصادر التسعير الرسمية للمراجعة وقت القرار: https://firebase.google.com/pricing ، https://cloud.google.com/run/pricing ، https://cloud.google.com/scheduler/pricing ، https://cloud.google.com/kms/pricing . لم تتحقق Codex من سعر حساب المالك أو عملته أو حجم استخدامه؛ لا رقم شهري مختلق ولا ضمان تكلفة صفر. الميزانية والتنبيهات ليست سقف إنفاق مانعاً. حدود callables الحالية maxInstances=15 لكل دالة، ولا تشكل حداً إجمالياً للفواتير؛ حدود triggers والسعة تحتاج مراجعة في طلب التشغيل.

لا يُطلب تفويض مالي أعمى الآن. بعد قراءة billingInfo والخدمات والاستخدام المستهدف يقدم **طلب موافقة واحد** يحدد: هل Blaze مفعل أصلاً أو سيُفعّل، APIs والموارد التي سيُنشئها النشر، منطقة وهوية الدوال، جدول الإشعارات، نطاق بيانات الاختبار، حد الميزانية الذي يختاره المالك والتنبيهات، تقديراً مبنياً على استخدام متفق عليه وروابط الأسعار، ونقاط التراجع. حتى ذلك الحين: نشر غير مفوض وتفعيل فوترة غير مفوض.

## التراجع والقبول الحقيقي

اتبع BACKUP_RESTORE_ROLLBACK_AR.md دون import/wipe/حذف أعضاء أو إعادة bootstrap. عند فشل النشر لا تعالج الفشل بفتح القواعد أو تعطيل App Check أو العودة إلى إصدار يزيل موافقة Google أو حظر Click. التراجع منفصل للمصدر وFunctions والقواعد وتطبيق العميل؛ لا يرجع بيانات Firestore/Auth أو إشعاراً أرسل فعلاً. نشر أول مرة بلا إصدار سابق يتطلب قرار containment/إصلاح أمامي، وليس ادعاء rollback جاهز. احتفظ بالفهارس الإضافية الآمنة حتى مراجعة توافقها؛ لا حذفها آلياً.

بعد النشر المفوض وقبل إعلان اكتمال المرحلة:

- دخول المدير الفعلي من كل منصة مستهدفة؛ رفض password sessions والـApp Check المفقود/غير الصالح فعلياً. تشغيل الهاتف/المتصفح وليس Functions.run فقط.
- أربعة حسابات Google حقيقية مخولة يحددها المالك للأدوار الأخرى، وليست Google identities مصطنعة؛ دخول→pending بلا بيانات داخلية→موافقة المدير وتعيين الدور/الفريق→active. رفض وتغيير صلاحية وتعطيل وسحب الوصول فوراً، وحماية المدير الأخير.
- إنشاء طلب اصطناعي واحد لكل دور، حدود الرؤية والتعديل والمبالغ والفرق والحالات، منع الحذف، Audit والتعارض وعدم التكرار. هذه تغيّر بيانات المشروع المشترك وتحتاج تفويض الاختبار ضمن طلب التشغيل.
- FCM على Web/Android/iOS بالأذونات وVAPID وService Worker وAPNs عند تهيئتها، دون طباعة أو Click. لا إرسال إشعارات من إجراء الجرد.
- التحقق من monitoring وأخطاء التشغيل ونسخة الإصدار الفعلية وretention والتراجع قبل قبول المالك. لا اختبار شركة أو شحنات أو نشر متاجر.

**قرار المرحلة:** التحضير البرمجي لا يساوي تشغيل Firebase. لا إغلاق للمرحلة قبل قراءات Cloud Shell المخولة، وقرار النشر/التكلفة، ونشر Backend الموافق واختبارات القبول الحقيقية. لا تعاد مرحلة تأسيس المدير.
