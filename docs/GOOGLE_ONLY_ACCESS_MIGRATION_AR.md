# دخول Google فقط وموافقة الانضمام — خطة ترحيل آمنة

> تحديث مصادقة المشغل: [إصلاح جلسة gcloud](GCLOUD_SESSION_AUTH_FIX_AR.md). مسار Cloud Shell والفحص الجاف الافتراضي يعيدان استخدام الجلسة البشرية الحالية دون ADC إضافي، والفحص باستخدام ADC المُدار يحتاج --managed-adc صراحةً. لا تغييرات في سياسة Google أو شروط العضوية أو التفويض.

المصدر: تغيير على audit/production-readiness بعد e290b44؛ التنفيذ والاختبار محليان فقط. لم نغيّر Firebase Console أو بيانات المشروع velnix-6c1a2، ولم ننشر Functions أو القواعد. يجب نشر العميل والقواعد وBackend المتوافقين في عملية مخولة لاحقاً؛ رفع المصدر إلى Git لا يفعّل هذا النظام على Firebase.

## العقد والسلوك

- شاشة Live تحتوي زر «المتابعة باستخدام Google» فقط. لا كلمة مرور أو استعادة أو إنشاء موظف بكلمة مرور. يبقى Demo محلياً منفصلاً. يحتفظ الزر ببوابة VELNIX_GOOGLE_ENABLED؛ الملفات المحلية السابقة ذات false تحتاج true بعد إعداد Google، ولا يفعّل ذلك مزود Firebase تلقائياً.
- كل callable خاص بالمستخدم يحتاج token صادر عن Firebase بمزود google.com وemail_verified=true، ثم عضوية active ودور معروف من Firestore لكل طلب؛ لا تفويض من custom claims أو بيانات العميل. Email/Password قد يصادق في Firebase أثناء الترحيل لكنه لا يمنح وصولاً إلى Backend الجديد. endpoints الشركة المجدولة/webhook تبقى على آلياتها القائمة ولا تتحول إلى تسجيل موظفين.
- joinSession يحتاج Google موثقاً ويقرأ سجل Auth للمستخدم نفسه، ويتحقق من provider/emailVerified/disabled وتطابق بريد Google مع البريد الأساسي. لا يقبل UID أو بريداً أو اسماً أو دوراً من payload. تغيير البريد إلى هوية غير متطابقة يوقف الانضمام حتى المراجعة.
- طلب الانضمام joinRequests/{uid} يحمل الاسم والبريد من Auth وحالة pending؛ لا دور أو permissions أو عضوية فعالة. التكرار المتزامن لا ينشئ طلباً أو حدثاً ثانياً. الطلب المرفوض يبقى rejected عند إعادة الدخول ولا يعاد تقديمه تلقائياً؛ إعادة فتحه ليست وظيفة مضافة في هذا النطاق.
- المدير العام النشط فقط يقرأ قائمة pending المرقمة ويقرر. الاسم للعرض ولا يثبت هوية الموظف؛ يجب مطابقة البريد الموثق مع الشخص المعتمد قبل الموافقة. المدير المفوض manageEmployees لا يوافق ولا يرفض، ويحتفظ بصلاحياته السابقة لتعديل الموظفين المعتمدين ضمن حدود التفويض القائمة.
- decideJoinRequest يرفض القرار على نفسه أو طلب عولج أو عضوية موجودة. الموافقة تتحقق من أحد الأدوار الخمسة والصلاحيات والفريق الحالي، ثم تنشئ active=true والدور والصلاحيات والفريق وقرار الطلب وAudit داخل معاملة واحدة. تعارض موافقة/رفض لا ينتج عضوية مزدوجة. supervisor صالح ونشط ودوره sales، ولا يمكن الإشراف الذاتي؛ ربطه يحدّث authorizationVersion.
- saveMember يعدّل عضويات موجودة فقط؛ لا ينشئ Auth users أو كلمات مرور. تبقى حماية آخر مدير عام نشط والتفويض المحدود وسجل member.updated. تعطيل العضوية يُحفظ أولاً، فيمنع الطلب التالي حتى لو فشل تحديث Auth أو revokeRefreshTokens.
- قواعد Firestore تسمح بقراءة وثيقة العضوية وقرار الانضمام لصاحبهما فقط؛ لا list أو write أو delete. الطلبات والشركات والمفاتيح والتدقيق والإشعارات تبقى ممنوعة مباشرة من SDK. pending/rejected/disabled لا يمكنهم دخول callable للبيانات الداخلية.
- العميل يتابع عضويته وقرار طلبه؛ عند تغيير سياسة العضوية يغلق المسارات الداخلية ويعيد تحميل السياسة، والخادم يعيد فحصها دون انتظار تجديد token. لا يمكن سحب بيانات سبق أن شاهدها مستخدم مخول؛ الجهاز الفعلي وحالات انقطاع الشبكة تبقى ضمن قبول5B.

## ترحيل الحسابات الحالية دون فقد الإدارة

**لا تنشر Backend الذي يرفض كلمة المرور قبل إثبات دخول مدير عام قائم عبر Google على UID نفسه.** لا تعطّل Email/Password الآن ولا تحذف أو تعيد إنشاء حسابات Auth/الأعضاء/الطلبات.

1. المالك يراجع، بقراءة مخولة، UID كل مدير عام نشط في members وربطه بسجل Authentication. يسجل داخلياً جدول UID والدور والحالة ووجود provider google.com دون تصدير كلمات مرور أو بيانات شخصية إلى Git.
2. جهّز Google provider وOAuth/Authorized Domains وSHA والتوقيع وApp Check لكل منصة بموافقة منفصلة. تحقق فعلياً من تسجيل Google للمدير العام ومن أن UID المعاد يطابق UID عضويته؛ تشابه البريد وحده ليس دليلاً. يفضّل وجود مدير عام احتياطي معتمد قبل الانتقال.
3. إذا كان Google مربوطاً بالفعل إلى UID الموظف الحالي، تبقى العضوية ودوره وفريقه وملكية طلباته كما هي؛ لا backfill ولا إعادة موافقة تلقائية ولا تغيير للـUID. غياب approvalStatus في العضويات القديمة لا يلغي العضوية الموثوقة الحالية.
4. إذا لم يكن Google مربوطاً: يحتاج ربط provider على **نفس حساب Auth** بجلسة مؤقتة موثقة وإعادة مصادقة، بواسطة مسار Firebase الرسمي ومشغل مخول. لا يعتمد الكود الحالي أي دمج تلقائي بحسب البريد، ولا يضيف واجهة كلمة مرور لهذا الغرض. يجب تأكيد UID بعد الربط قبل النشر. هذه عملية خارجية غير منفذة وتحتاج موافقة.
5. إذا نتج UID جديد مختلف، يتوقف الانتقال؛ يبقى الحساب الجديد pending ولو طابق البريد. لا تنقل role أو createdBy أو audit أو الفرق آلياً. حل تعارض/ربط الحساب يحتاج خطة منفصلة مصادقاً عليها، ولا تجرّب الحذف/الدمج على بيانات حقيقية.
6. جهز نسخة رجوع متوافقة من العميل وFunctions والقواعد ومراجع الإصدارات؛ لا تعيد إرسال شحنات أو تعديل طلبات في rollback. فشل Google أو App Check أو غياب إدارة مخولة يمنع النشر ولا يعالج بمنح GM تلقائياً.
7. بعد نشر مخول لاحق واختبار المدير العام والأدوار الخمسة والموافقة/الرفض والتعطيل على أجهزة فعلية، واعتماد المالك: عندها فقط يُطلب تفويض مستقل لتعطيل Email/Password من Authentication → Sign-in method. لا توجد خطوة تعطيل تلقائية في الكود.

## تجهيز أول مدير عام عند غياب الإدارة فقط

functions/scripts/bootstrap_admin.js لم يعد ينشئ حساباً أو كلمة مرور. يحتاج هوية مشغل مُدارة مخولة، وتأكيد المشروع وVELNIX_ADMIN_GOOGLE_UID الذي تحقق المالك من ملكيته مستقلاً. يقرأ سجل Auth ويتحقق من Google والبريد الموثق وعدم التعطيل؛ لا يبحث بالبريد ولا يختار أول مستخدم مسجل.

الفحص الافتراضي dry-run قراءة فقط؛ الكتابة تحتاج --apply وتفويضاً منفصلاً. يرفض التنفيذ إذا وجدت أي عضوية للـUID أو أي مدير عام أو bootstrap lock، فلا يستعمل لترقية عضو حالي أو استبدال إدارة موجودة. الكتابة المخولة لاحقاً تنشئ قفل bootstrap والعضوية وAudit داخل معاملة، وتغلق pending لهذا UID إن وجد؛ لا تتجاوز طلباً مرفوضاً. لا تعطّل حماية رفض bootstrap لإصلاح قفل إدارة قائم؛ اتبع الترحيل أعلاه بمشغل مسؤول.

مثال أسماء المتغيرات فقط، دون قيم أو اعتمادات: GCLOUD_PROJECT، VELNIX_BOOTSTRAP_CONFIRM_PROJECT، VELNIX_ADMIN_GOOGLE_UID. الأمر node functions/scripts/bootstrap_admin.js فحص قراءة وقد يحتاج IAM؛ لا يشغّل على المشروع الحقيقي في هذه المهمة. --apply عملية تغيير منفصلة وليست جزءاً من طلب التهيئة أو الاختبارات.

## متطلبات Console لاحقاً

- Project settings: مطابقة التطبيقات الثلاث النشطة، com.mode2094.velnix، SHA1/SHA256 لشهادة الاختبار/التوزيع الصحيحة؛ iOS URL scheme وclient IDs؛ لا تطبيقات مكررة.
- Authentication → Sign-in method: تهيئة Google ومعلومات الدعم بإذن منفصل؛ **Email/Password يبقى كما هو**. Authorized Domains للويب، واختبار Google UID للمدير العام قبل الانتقال.
- App Check: Play Integrity وDeviceCheck وreCAPTCHA v3؛ site key العام للويب ما زال اعتماداً مفتوحاً وفق5A. لا debug في release ولا تعطيل enforcement لتجاوز مشكلة.
- إعدادات البناء العامة المحلية: VELNIX_GOOGLE_ENABLED=true بعد التهيئة، وGOOGLE_WEB_CLIENT_ID الصحيح عند حاجة native server client؛ لا Google client secret في التطبيق. Google/FCM لا يفعّلان تلقائياً بتغيير هذا العلم.
- مراجعة إصدار Functions في europe-west1 والقواعد والفهارس الموجودة ثم تفويض نشر مستقل ومتطلباته المالية؛ Backend هنا ليس مثبتاً أنه منشور. قائمة pending تستخدم status مع document ID الافتراضي ولا تضيف composite index جديداً.
- التحقق من تسجيل الأجهزة والخروج والإشعارات على أجهزة فعلية؛ هذه التغييرات لا تغلق قبول الأجهزة أو IAM أو الخدمات الحقيقية. Click يظل محجوباً دون generic_v1 بديل.

## دليل الاختبار وحدوده

اختبارات Google الجديدة تستعمل signInWithIdp على Auth emulator مع assertion اصطناعي، وتتحقق من Firebase token وسجل provider في المحاكي؛ لا تتصل بـGoogle OAuth الحقيقي. اختبارات Backend عبر callable.run لا تثبت App Check الحقيقي أو IAM، واختبارات Widgets لا تثبت تدفق Google على جهاز.

تغطي الانحدارات إنشاء pending دون دور، انتحال payload وprovider والبريد غير الموثق، منع الوصول الداخلي، حصر الموافقة بالمدير العام، الأدوار الخمسة والفريق، الموافقات المتزامنة وسباق الموافقة/الرفض، بقاء الرفض وإعادة الدخول، تغيير الدور والتعطيل على token نفسه، رفض دمج UID مختلف، pagination، قواعد منع تعديل القرار، وbootstrap الجاف والمتزامن. تفاصيل الأعداد والنتائج تحفظ في دليل النتائج النهائي.

النتيجة المحلية النهائية:323 Flutter و58 Node و64 محاكي و12 Python و36 PDF رقمية ناجحة؛ Web وAndroid Debug بنمط Live وGoogle enabled ناجحان في البناء فقط. التفاصيل والقيود في [دليل التحقق](evidence/google-only-approval-validation.json). لا نجاح CI مفترض ولا تجربة Google حقيقية أو بناء iOS.
