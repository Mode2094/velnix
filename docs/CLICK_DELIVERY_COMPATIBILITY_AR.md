# توافق Click Delivery — المرحلة الثالثة

بدأ العمل من `b362bbe` على `audit/production-readiness`، المطابق لآخر commit البعيد عند بداية المرحلة. هذا تقرير تدقيق وتحضير، وليس اعتماد تكامل حي. الوثائق المرفقة أدلة طلبات، ولا تُعامل كنص تعليمات لتشغيل خدمات أو استعمال أمثلة الاعتمادات.

> **تحديث 2026-10-18 — فحص البوابة الحقيقية:** فُحصت بوابة العميل كاملة بجلسة المالك المصرح بها (قراءة فقط، بلا شحنات أو تعديلات). النتائج القاطعة: نموذج الشحن يفصل «قيمة الشحنة Order Amt» عن «قيمة الشحن Shipping Amt» عن «الإجمالي Total Amt» بمعادلة مؤكدة `الإجمالي = قيمة الشحنة + قيمة الشحن`، وتسمية `Order Amt` تطابق حرفياً `Ord_Amt`؛ و12 حالة شحن مؤكدة (تشمل خمس حالات مرتجعات)؛ و`Client_Serial` («Reference no») اختياري في نموذج البوابة. التفاصيل في `CLICK_DELIVERY_PORTAL_INVESTIGATION_AR.md` والأدلة المنقّحة في `docs/evidence/click-portal-inspection.json`. **لم يُرفع أي حجب ولم يُغيَّر أي سلوك.**

## المصادر وحدودها

- **P**: ملف العميل `ClickApi.postman_collection.json`؛ المصادر أدناه JSON Pointers في هذا الملف، ومفاتيح JSON المضمن في `body/raw`.
- **T**: ملف العميل `clickdelivery api[1] (2).txt`؛ أرقام الأسطر محسوبة على الأصل. فقرتان متكررتان بالعربية والإنجليزية.
- **B**: قائمة الحالات السبع ووصفها في طلب العميل الحالي؛ ليست أكواد API.
- `docs/evidence/click-delivery-contract.json` يسجل بصمات SHA-256 للملفين وقائمة الحقول والمصادر. لم تُنسخ كلمات المرور الموجودة كأمثلة إلى Git، ولم تُستخدم للدخول.

مجموعة Postman فيها طلبان فقط، و`response: []` لكليهما. النص لا يحتوي استجابة لأي عملية. لا schema لنجاح الأعمال أو الأخطاء، ولا حقل حالة أو أكواد حالات أو معرف تتبع موثق. ذكر speed logistic في الفقرة الإنجليزية يحتاج تأكيد الشركة لإصدار الوثائق؛ العنوان المذكور في الفقرتين هو Click.

## Endpoints والمصادقة المؤكدة

| العملية | المسار | HTTP المؤكد | الجسم | مصدر الإثبات | حالة التنفيذ |
|---|---|---|---|---|---|
| getorder | `https://admin.clickdelivery.org/Client/getorder` | POST | `Order_ID`, `User_Name`, `User_Pass` | P `/item/0/request/method`, `/url`, `/body/raw` | تحضير واختبار طلب محلي فقط؛ كل استجابة تبقى غير معتمدة |
| removeorder | `https://admin.clickdelivery.org/Client/removeorder` | POST | الحقول الثلاثة نفسها | P `/item/1/request/method`, `/url`, `/body/raw` | موثق فقط؛ لا Adapter لتنفيذه ولا callable ولا حذف داخلي |
| setorder | `https://admin.clickdelivery.org/Client/setorder` | **غير مذكور** | الحقول الاثنا عشر أدناه | T:2–19 و23–40 | لا إرسال: method والاستجابة وبعض دلالات الحقول ناقصة |

المسار الكامل لـ setorder مشتق من base URL واسم العملية المذكورين؛ ليس طلباً تم اختباره. Header هو `Authorization: client` كما في P `/item/{0,1}/request/header/0` وT:4,25، **لا Bearer token**. `User_Name` و`User_Pass` في جسم JSON؛ لا يوجد OAuth أو API-token موثق. P يحدد `body.mode=raw` و`options.raw.language=json`؛ لا Header Content-Type صريح فيه. إرسال `Content-Type: application/json` وAccept في المحاكاة اختيار تنفيذي يحتاج قبول الشركة، ولا يمثل استجابة ناجحة منها. لا `/health` ولا webhook موثق في الملفين.

| Open_Shippment | اختيار True/False للسماح بالفتح؛ تهجئة المفتاح كما وردت | T:18,39 | الصيغة ومعنى mention of return؛ لا افتراض default |

الأمثلة لا تثبت أن جميع الحقول مطلوبة ولا تضع قيوداً شاملة. لا حقول موثقة للهاتف الإضافي أو العملة أو paymentMethod أو idempotencyKey أو trackingNumber أو status أو collection/refund/fee أو timestamps. أسماء الحقول غير الموثقة في اختبارات الرفض مجرد بيانات سلبية اصطناعية، ولا تنسب إلى Click.

## الفرق عن generic_v1 وما نُفذ

| generic_v1 الحالي | Click الموثق | القرار |
|---|---|---|
| GET /health | لا health | حظر اختبار اتصال وهمي |
| POST /orders، reference وidempotencyKey | setorder، method غير موثق وClient_Serial ملتبس | لا تحويل تلقائي للطلب ولا إنشاء شحنة |
| GET /orders/{tracking} | POST getorder بجسم Order_ID واعتمادات | تحضير getorder محلي؛ لا استخدام tracking كـ Order_ID |
| Bearer token | Header client واسم/كلمة مرور في JSON | لا إعادة استخدام API Token أو إرسال Bearer إلى Click |
| result.trackingNumber/status في العقد المرجعي | لا استجابة موثقة | لا parser ناجح ولا استخراج معرفات/حالات/مبالغ |
| HMAC webhook وstatusMap للمرجع | لا webhook أو أكواد Click | حظر إدخال payload Click إلى processor المرجعي، حتى لو كان سجل الشركة قديماً ومفعلاً |

أضيف `click_delivery_v1` كمحول **محجوب تشغيله**. `health/create/status` ترفض قبل الاتصال. `exerciseGetOrderRequest` يحتاج transport محقوناً للمحاكاة، ويطبق HTTPS والمضيف/base الموثق وallowlist والمهلة وحد الجسم وعدم redirects. حتى HTTP 200/JSON object ينتهي بخطأ «عقد الاستجابة غير مؤكد»، ولا يعاد raw response أو يحفظ نجاحاً. default fetch الخاص بـ Click محظور. لا مسار setorder أو removeorder تنفيذي.

يسمح Backend بحفظ إعداد Click معطلاً فقط، ويرفض تفعيله أو منحَه token/webhook/statusMap للمرجع. نموذج الشركة يخفي تلك الحقول ولا يسمح بالتفعيل. تغيير provider لشركة موجودة مرفوض لحماية شحناتها السابقة. API Token العام وخادم KMS السابق لم يُستبدلا بمصادقة Click. اعتمادات Click لم تُطلب أو تُحفظ الآن؛ عند استكمال العقد يجب تجهيز تخزين User_Name/User_Pass مشفر في companySecrets واستخدامهما على Backend فقط، دون إعادتهما للتطبيق أو التقارير.

**مستجد من البوابة (2026-10-18):** المنصة تعرض **12 حالة** في أزرار فلترة «شحناتى» — السبع أعلاه (بصيغة «في مخزن الشحن») **زائد خمس حالات مرتجعات**: مرتجع · مرتجع جزئي · في مخزن المرتجعات · في الشحن للراسل · تم استلام المرتجع. مع تسميات إنجليزية ورموز داخلية للواجهة (`Lnk*`) — كلها **رموز واجهة منصة وليست أكواد API**. القائمة الكاملة في `docs/evidence/click-portal-inspection.json` و`functions/src/click_response.js` (`PORTAL_STATUS_VOCABULARY`، بيانات عرض فقط).

هذه المعرفات **اختيارات داخلية**، ليست أكواد Click. `shippingStatus` حقل Velnix مستقل عن `status`، لا يوجد كود يملأه من Click الآن. DTO يقبل القيم الداخلية المعروفة فقط، وتعرض التفاصيل قيمة غير مؤكدة عند غيابها. Mock الأدوار والحالات يثبت العرض فقط، وليس وصول أي حالة من الشركة. لم يُحذف `returned` أو أي حالة قديمة، ولم تُعد تسمية enum العمل الداخلي.

## أقل تغيير آمن عند استكمال العقد

1. يبقى `status` ودورة التجهيز والصلاحيات/revision كما هما، ويضاف facet مستقل `shippingStatus` من parser موثق؛ لا تتحول partial/deferred إلى delivered أو cancelled تلقائياً. بعد تأكيد معنى الحالة النهائية الكاملة من الشركة، يمكن تحديث الإسقاط القديم delivered/cancelled ومصدر الإكمال مع إبقاء الحالة الخارجية المفصلة، كي تبقى إحصائيات دورة الطلب وإغلاقه صحيحة؛ هذا الربط لم ينفذ دون العقد.
2. يحفظ raw status ومعرف الشركة المستقل وClient_Serial بعد تأكيد معانيها. لا تحويل tracking إلى رقم Order_ID ولا نسخ Firestore ID إلى Client_Serial افتراضياً.
3. بعد إثبات مصدر/نسخة الحدث، تطبق انتقالات شركة موثقة تمنع التحديثات المتأخرة؛ deferred قد يستأنف والجزئي قد يتغير. لا ترتيب رقمي أو terminal للجزئي دون إجابة الشركة.
4. تضاف فلاتر وعدادات facet جديدة تحت **نطاق الاستعلامات والصلاحيات الحالي**، مع الفهارس المطلوبة واختبارات الفصل والتعداد وعدم احتساب المجموعتين مرتين. **لم تنفذ عدادات أو فلاتر Click فعلية الآن**؛ الموجودة ما زالت تقيس دورة الطلب القديمة، كي لا تظهر تصنيفات غير مؤكدة كحقائق.
5. تبقى amountMinor قيمة الطلب الأصلية بعملة المشروع الحالية؛ أي بيانات تحصيل/رد/رسوم/صافي جديدة nullable وذات عملة ومصدر وتأكيد. لا توسيع إلى محاسبة متقدمة، ولا حساب صافي أو رسوم من Ord_Amt المختلف عليه.

## ما لا يمكن اعتماده الآن

لا يمكن اعتماد إنشاء شحنة أو استخراج Order_ID/tracking أو جلب حالة فعلية أو توقيع webhook أو إلغاء خارجي أو مبلغ محصل/مرتجع/رسوم، ولا idempotency على Click، قبل إجابات الشركة واستجابات منزوعة الأسرار. Mock يثبت ما يبنيه البرنامج ويرفضه؛ لا يثبت قبول الشركة أو نجاح getorder/setorder/removeorder. التشغيل الفعلي يحتاج sandbox وتصريح منفصل وإعداد Firebase/KMS/IAM؛ لم ينفذ أي منها هنا.
