## 1. جميع المحاولات الآمنة التي نُفذت ونتائجها

### 1.1 مصفوفة الطلبات الحيّة على `/Client/getorder` (نتائج فعلية، بلا تنقيح للمغلّفات)

| # | الشرط | HTTP | رسالة التطبيق |
|---|---|---|---|
| P1 | POST JSON + `Authorization: client` (الشكل الموثق حرفياً) | **401** | `{"error":{"Message":"بيانات مستخدم غير صحيحة"}}` |
| P2 | نفسه بدون رأس Authorization إطلاقاً | **401** | `{"error":{"Message":"Unauthorized"}}` |
| P3 | جسم form-urlencoded + `Authorization: client` | **401** | `{"error":{"Message":"بيانات مستخدم غير صحيحة"}}` |
| P4 | GET + `Authorization: client` (عزل توجيه الطريقة) | **405** | `{"Message":"The requested resource does not support http method 'GET'."}` |
| P5 | جسم JSON فارغ `{}` + `Authorization: client` | **401** | `{"error":{"Message":"بيانات مستخدم غير صحيحة"}}` |
| P6 | `Authorization` بقيمة بحرف أول كبير (حساسية الحالة) | **401** | `{"error":{"Message":"Unauthorized"}}` |
| P7 | `Authorization` بقيمة حرفية خاطئة | **401** | `{"error":{"Message":"Unauthorized"}}` |
| **A1** | **POST JSON + `Authorization: client` + زوج اعتماد الحساب التجريبي المصرح به (قيمه مستبعدة)** — طلب واحد فقط | **401** | `{"error":{"Message":"بيانات مستخدم غير صحيحة"}}` |

**قراءة المصفوفة:**
1. **الرأس `Authorization: client` بوابة أولى حرفية وحساسة لحالة الأحرف**: غيابه أو أي تغيير فيه ⇒ `"Unauthorized"` قبل أي فحص اعتماد.
2. عند اجتياز البوابة يصل الطلب إلى **فحص بيانات الدخول** ويكون الرد لكل زوج جُرِّب — **بما فيه زوج الحساب الرسمي نفسه (A1)** — «بيانات مستخدم غير صحيحة».
3. **نوع ترميز الجسم لا يغيّر النتيجة** (JSON وform متماثلان) ⇒ المشكلة ليست في شكل الطلب.
4. الـ401 **من طبقة التطبيق** لا من طبقة HTTP: لا يوجد رأس `WWW-Authenticate`، والمغلّف JSON من IIS/ASP.NET (`Microsoft-IIS/10.0` + `X-AspNet-Version: 4.0.30319`).
5. GET يعزل 405 الخاصة بالطريقة عن منطق المصادقة تماماً.
6. **A1 هو الفصل الحاسم بين «أمثلة فقط» و«الحساب الحقيقي»:** الطلب الواحد بالحساب الرسمي انتهى بنفس رسالة رفض الاعتماد ⇒ ليس الأمر تخصيصاً للأمثلة المنشورة.

### 1.2 فحوص البوابة (قراءة فقط بحساب المالك)

| الفحص | النتيجة |
|---|---|
| أي قسم/إعداد API في شاشات العميل | **لا يوجد** (لا إعدادات، لا مفاتيح API، لا تفعيل تكامل، لا مساعدة تربط البوابة بـ`/Client/`) |
| «معلومات المستخدم» | الدور: **عميل** · الفرع: الرئيسي · خيار **تغيير كلمة المرور** فقط |
| إدارة المستخدمين | النموذج يتيح إنشاء مستخدمين فرعيين (اسم / **اسم الدخول أو رقم الموبايل** / كلمة مرور) — لا نوع «API» ولا صلاحيات تكامل |
| بحث في صفحات العميل وجافاسكربت الثيم | صفر إشارة إلى `/Client/` أو `getorder` (الوحيد: مفتاح Google Maps في الثيم، لا علاقة له) |

### 1.3 مراجعة الكود المحلي (Velnix)

- `vendorRequest` يبني لـClick: `POST` + `Authorization: client` + `Content-Type: application/json` + `Accept: application/json` + جسم JSON بالأسماء الموثقة حصراً.
- `getOrderBody` يرفض `Order_ID` خارج الأعداد الصحيحة الموجبة، ويشترط `User_Name/User_Pass` نصّيين غير فارغين.
- **أُضيف اختبار تثبيت Wire-Format** يلتقط الطلب الفعلي على خادم محلي ويؤكد: method وpath والرأس الحرفي و`Content-Type` و`Accept` ومفاتيح الجسم الثلاثة بالضبط — فلا يمكن لأي انحدار مستقبلي تغيير بنية الطلب دون كسر الاختبار.
- الكود الجديد يوثّق المغلّفين المكتشفين الآن ويفرّق بينهما برمجياً: `authFailureReason()` ⇒ `authorization_header_invalid` مقابل `credentials_invalid` — بلا أي سلوك نجاح.

## 2. هل انحلت مصادقة API؟

**لا — وبإجابة قاطعة على السؤال الحاسم: المصادقة فشلت فعلاً ببيانات الحساب الحقيقي، لا بالأمثلة فقط.**

- طلب واحد (A1) بزوج اعتماد الحساب التجريبي المصرح به وبالشكل الموثق حرفياً ⇒ **401 + «بيانات مستخدم غير صحيحة»** — وهي رسالة **رفض الاعتماد من طبقة التطبيق** بعد اجتياز بوابة `Authorization: client` (لا «Unauthorized» الخاصة بالبوابة).
- هذا يعني أن الفشل **ليس** في شكل الطلب (P1/P3)، ولا في الرأس (P1 مقابل P2/P6/P7)، ولا في الطريقة (P4)، ولا في الترميز — كل ذلك مثبت منفصلاً.
- وكانت الملاحظة السابقة صحيحة بالمعنى التقني (المصفوفة استخدمت الأمثلة المنشورة)، والآن أُضيف الاختبار الحقيقي: **النتيجة نفسها** ⇒ الرفض يتعلق بزوج الاعتماد المُرسل لواجهة `/Client/` وليس بأمثلةٍ عامة.
- ما لا تستطيع هذه الجولة حسمه: **هل الاعتماد الصحيح لواجهة `/Client/` يختلف عن اعتماد البوابة؟ وهل يحتاج الحساب تفعيل واجهة API عند Click؟** لا يوجد أي سطح تفعيل API في البوابة (مثبت قراءةً)، ولا يجوز تخمين صيغ اعتماد بديلة. الحسم يقع عند المزع أو بتزويد المالك للصيغة الصحيحة إن كانت مختلفة.

**لا نقول الآن «يحتاج تفعيلاً» كحكم نهائي** — نقول بدقة: **الزوج المُرسل (كما زوَّدنا المالك) مرفوض بـ401 من فحص الاعتماد، ويلزم تأكيد المزع/المالك للاعتماد الصحيح للـAPI.**

## 3. هل ثبت خطأ في Velnix؟

**لا.** لا خطأ في تكوين طلب المصادقة:
1. البنية مطابقة للمواصفة الحرفية (Postman + ملف التعليمات): POST، الرأس `client`، الحقول الثلاثة بأسمائها الحرفية بلا إضافات.
2. سلوك الخادم يتغيّر بشكل مقصود ومنفصل حسب اجتياز البوابة (P1 مقابل P2/P6/P7) ⇒ الطلب "يُفهم" ويعبر البوابة كما صُمِّم.
3. لم يُغيَّر أي سطر في مسار الإرسال؛ الإضافة الوحيدة توثيق + تصنيف المغلّفين + اختبارات.
4. الحجب قائم: لا `setorder`، لا `removeorder`، لا إنشاء/إلغاء، لا قرار مالي، لا إعادة إرسال.

## 5. هل نحتاج تفعيلاً أو معلومة من Click فعلًا؟

**نعم — بند حاسم واحد وثلاثة تابعة، بصياغة دقيقة بعد اختبار A1:**

1. **[حاسم] تأكيد الاعتماد الصحيح لواجهة `/Client/` للحساب 1603.** زوج الاعتماد المُرسل (كما زُوِّدنا) مرفوض بـ401 من فحص اعتماد التطبيق، بينما بوابة العميل تعمل به. على المزع/المالك حسم واحد من اثنين:
   - هل اعتماد `/Client/` هو نفسه اعتماد البوابة (وعندها يلزم التحقق من تدوير كلمة المرور أو صيغة اسم الدخول)، **أو**
   - أن واجهة `/Client/` تحتاج اعتماداً مستقلاً/تفعيلاً للحساب يُمنح من جهة Click.
   لا يمكن حسم أيهما محلياً، والبوابة نفسها لا تعرض أي إعداد API.
2. **[أثناء الحل] أكواد حالات `getorder`** مربوطة بالحالات الاثنتي عشرة المثبتة من البوابة (سؤال سابق قائم).
3. **[أثناء الحل] دلالة `Ord_Amt`** — تأكيد الترجيح القوي (قيمة الشحنة + شحن من قائمة أسعار Click) بشحنة API واحدة مع تقرير التسعير (سؤال سابق قائم).
4. **[أثناء الحل] idempotency `Client_Serial`** وسلوك التكرار (سؤال سابق قائم).

**ما لن يُنفذ:** أي محاولة اعتماد إضافية، أو تخمين صيغة اسم دخول، أو اختبار أزواج بديلة — حتى تأتي المعلومة من المالك/المزع.
