# مراجعة وتسليم هندسي — Velnix v0.5 — 14 أكتوبر 2026

## ما تم توثيقه وفحصه محلياً

1. تم الاحتفاظ بنسخة الواجهات v0.4 كما هي للمعاينة بواسطة `VELNIX_MODE=demo`.
2. مسار حي مستقل يعتمد على Firebase Auth وCloud Functions، حتى لا يستطيع العميل تبديل الدور المحلي للوصول إلى طلبات غيره.
3. جميع إنشاءات الطلبات وتعديلاتها وحالاتها تمر من الخادم وتُوثَّق؛ لا توجد دالة حذف طلب.
4. 5 أدوار: مدير عام/مدير/مستودع/مبيعات/مدخل بيانات، وإنشاء طلب متاح لكل دور مفعل.
5. المبيعات ترى طلباتها وطلبات موظفي إدخال البيانات المرتبطين بها (لقطة ارتباط وقت إنشاء الطلب)، والمستودع يمكنه متابعة الحالات التشغيلية، ومنع الترقيات غير المصرح بها.
6. بطاقات مجموعات الطلبات وبطاقات كل شركة توصيل وحالاتها، مع الملاحة لقائمة الحالة داخل الشركة.
7. عميل Firestore لا يستطيع قراءة الطلبات أو الشركات أو الأسرار أو السجلات مباشرة، وكل الاستعلامات تمر عبر Cloud Functions مصرح بها.
8. حفظ المبالغ بعدد صحيح من الفلس (الدينار الأردني = 1000 فلس)، مع عرضها بـ3 منازل عشرية.
9. Cloud KMS لمفاتيح التوصيل، منع URLs خارج whitelist، توثيق Webhook عبر HMAC، إزالة التكرار، ومنع عكس طلب مغلق إلى حالة أقدم.
10. مجموعة اختبارات Node.js نجحت 9/9، وفحص صياغة JavaScript نجح.

## ما لم أتمكن من فحصه هنا

- `flutter pub get`, `flutter analyze`, `flutter test`, تشغيل جهاز Android أو متصفح حقيقي، أو اختبارات الوصول والواجهة بصرياً بعد البناء.
- تثبيت npm dependencies؛ اتصال registry.npmjs.org تعذر `EAI_AGAIN` في بيئة العمل.
- `firebase emulators:exec` أو نشر مشروع Firebase أو التحقق من Security Rules عبر المحاكي.
- الاتصال بشركة التوصيل الحقيقية؛ يتطلب Sandbox، عقد API، ومفاتيح صالحة.
- FCM Push / صوت الإشعارات عند إغلاق التطبيق، واستعادة كلمة المرور وMFA، ومراقبة الأعطال، وسياسات الاحتفاظ بالبيانات والنسخ الاحتياطي، واختبارات الأداء.

## مخاطر مهمة تمنع وصفه بأنه جاهز للإنتاج

- **التوافق مع API:** المحوّل Generic v1 افتراضي ويحتاج تخصيصاً لأسماء المسارات/حقول الحالات/التوقيع الخاص بمزود العميل؛ اختبار الاتصال `/health` لا يعني أنه سيعمل مع أي شركة.
- **الإحصائيات:** اللوحات ومجاميع الشركات تقرأ أحدث 1000 طلب لكل مجال عرض؛ تظهر إشارة «بيانات جزئية» إذا تجاوز العدد، ويجب إنشاء Aggregated Counters قابلة للتوسع قبل زيادة حجم التشغيل.
- **صلاحيات الفرق:** تم منع تغيير الدور أو مسؤول المبيعات لموظف لديه طلبات دون ترحيل؛ يلزم تصميم Migration وظيفة إدارية تدقيقها واضح إذا أراد العميل نقل الموظف بين الفرق.
- **التحديثات:** polling دوري مع جدولة واسترجاع أخطاء أساسي؛ يحتاج اختبار Vendor sandbox وسياسة retries/backoff/quotas حقيقية. تتطلب العمليات المالية مراجعة audit إضافية.
- **الأمان:** لا يُنشر App Check أو KMS قبل مراجعة أذونات الخدمات، الاختبارات وConfig التي تم توليدها ببيانات العميل.
- **التصميم:** النسخة الحية جديدة ومطوّرة عن v0.4؛ لم تمر مراجعة بصرية فعلية على هاتف أو لابتوب بعد.
