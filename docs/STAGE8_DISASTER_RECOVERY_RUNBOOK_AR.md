# Stage 8B — Runbook التعافي من الكوارث (Firestore / Velnix)

المستودع: `Mode2094/velnix` · المشروع: `velnix-6c1a2` · القاعدة: `(default)` · الموقع: `nam5`

**وثيقة إجراءات جاهزة للتنفيذ المستقبلي فقط. لم تُنفَّذ أي خطوة إنتاجية منها في هذه الجولة. أي خطوة سحابية تتحرك فقط بموافقة مالك صريحة ومنفصلة، وبعد استيفاء متطلبات قسم الاعتماد.**

---

## 0. حقائق يجب أن يعرفها كل منفّذ قبل البدء

| الحقيقة | الأثر |
|---|---|
| Click **غير منشور بالكامل** (`sendOrderToDelivery` غير موجود في الإنتاج) | لا يوجد مسار إرسال شحنات أصلاً؛ ابقَ عليه |
| `pushNotice` و`recoverPushes` **غير منشورتين** | لا FCM حقيقي حالياً؛ لا تعتمد الاستعادة على تعطيل غير قائم |
| PITR **معطّل** ولا توجد نسخ ولا جداول ولا Bucket تصدير | حتى تفعيلها بموافقة، **لا يوجد أي ضمان استرجاع سحابي** |
| نسخة Firestore **لا تشمل** Firebase Auth ولا KMS ولا IAM ولا GCS | لكل أصل مسار تعافٍ منفصل (أقسام 8) |
| استعادة أقدم من الحالة الفعلية | تُفقد كتابات ما بعد النقطة، وقد تعود `dispatchState`/`pushState` خلفاً |

## 1. تصنيف الحوادث

| الدرجة | المثال | مسار التعافي |
|---|---|---|
| **A — حذف/كتابة خاطئة محدودة** | حذف مجموعة طلبات بالخطأ، كتابة أبطلت حقل | PITR (عند تفعيلها) → تصدير نقطة زمنية → استيراد انتقائي إلى بيئة معزولة → تحقق → استيراد إنتاجي بموافقة |
| **B — تلف واسع/خطأ منطقي عمّ المنظومة** | ترحيل خاطئ أفسد بيانات كثيرة | نسخة مُدارة (يومية/أسبوعية) + استعادة كاملة أو PITR نقطة محددة |
| **C — فقدان القاعدة/المشروع** | إساءة إعداد، مشكلة مزوّد | استعادة نسخة مُدارة إلى قاعدة جديدة → تغيير مسار التطبيق (Release Manifest) → إعادة بناء الخدمات المحيطة |
| **D — فقدان غير مغطّى بالنسخة** | ضياع مفاتيح KMS، حذف مستخدمي Auth، تسريب اعتمادات Click | مسارات الأقسام 8 — لا تحاول «حلّها» بإعادة استيراد Firestore |

**قاعدة:** كل درجة تمر أولاً بـ«استرجاع معزول» (قاعدة/مشروع منفصل) للتحقق، ثم الاسترجاع الإنتاجي بموافقة.

---

## 2. المبادئ الثابتة (غير قابلة للتفاوض)

1. **لا إعادة إرسال `setorder` تلقائياً — أبداً.** أي طلب `dispatchState ∈ {sending, sent, needs_review}` يبقى محجوباً حتى مراجعة بشرية موثقة مقابل سجل المزوّد.
2. **لا حذف مستندات أثناء الاستعادة.** الاستيراد الرسمي دمج بطبيعته؛ الأداة المحلية لا تحذف شيئاً. أي تنظيف للأحدث من نقطة الاستعادة قرار مالك موثق.
3. **لا استعادة أولى إلى الإنتاج مباشرة.** دائماً: استرجاع معزول → تحقق → قرار.
4. **قبل أي استرجاع: عزل الأطراف الخارجة.** لا استرجاع بترتيبات تجعل triggers أو شركات توصيل أو إشعارات تعمل أثناء/بعد العملية دون مراجعة.
5. **كل قرار يُسجَّل:** نقطة الاسترجاع، سببها، من اتخذها، ما أُحدث من فقدان، سجل المراجعة البشرية للشحنات.
6. **لا أسرار في السجلات ولا في Git:** لا محتوى مستندات ولا اعتمادات ولا رموز في سجلات الحادث.

## 4. قائمة تحقق ما بعد الاستعادة (لا عودة للخدمة قبل اجتيازها)

| # | الفحص | القبول |
|---|---|---|
| 1 | اكتمال المجموعات والفرعيات | كل المجموعات المتوقعة موجودة: `members, joinRequests, orders(+events), companies, companySecrets, deliveryInbox(+events), notices, devices, auditEvents, idempotency, settings` (بحسب حالة التشغيل الفعلية قبل الكارثة) |
| 2 | العضويات والصلاحيات | `members`: كل `uid` يطابق مستخدم Auth فعلي؛ لا عضو «نشط» مطلوب إيقافه؛ لا مالكان نشطان بالمخالفة لأدبيات التمهيد |
| 3 | `settings/bootstrapState` + `settings/system` | متطابقان مع الواقع؛ لا قفل تمهيد معلّق يمنع الدخول |
| 4 | الطلبات المكتملة/المقفلة | `delivered/returned/cancelled` لم تُفتح؛ `revision` متسق |
| 5 | `dispatchState` | كل ما كان `sending/sent/needs_review` بقي محجوباً؛ لا تصفير؛ لا إعادة إرسال |
| 6 | idempotency | مفاتيح إنشاء الطلبات موجودة مع طلباتها؛ لا تصفير يدوي |
| 7 | auditEvents | لا حذف سجل؛ الفارق الزمني بعد نقطة الاستعادة مُوثَّق في تقرير الحادث |
| 8 | notices / devices | `pushState`: أي `pending/processing` تُراجَع يدوياً قبل أي تفعيل دفع؛ `devices` غير موثوقة → إعادة تسجيل بشري |
| 9 | companySecrets | فك تشفير تجريبي واحد (شركة واحدة) بمفتاح KMS الصحيح — بلا طباعة السر — لإثبات صلاحية المسار |
| 10 | deliveryInbox | أحداث المزامنة متسقة مع حالة الطلبات؛ لا أثر أحداث يتيمة |
| 11 | Firebase Auth منفصل | تسجيل دخول تجريبي موثق يعمل؛ UIDs مطابقة؛ disabled للإيقافات |
| 12 | الخروج إلى الشركات | لا مكالمات مزوّد أثناء وبعد التحقق؛ تسوية بشرية موثقة فقط |

## 5. Safe Recovery Mode — تعريف وإدارة

**المقصود:** وضع تشغيلي مؤقت بعد الاستعادة تُفتح فيه الخدمات تدريجياً وبشروط، فلا تعود أي قدرة خارجية خطرة تلقائياً.

| القدرة | الحالة الافتراضية بعد الاستعادة | شرط الفتح |
|---|---|---|
| دخول الموظفين والعمليات الداخلية | مغلقة حتى قسم 4 | اجتياز قائمة التحقق |
| Click (إرسال) | **محجوب** | إجابات D4/D7/D9/D10 + نشر المرحلة 3 + تسوية بشرية لكل `sending/sent/needs_review` |
| FCM (`recoverPushes`/`pushNotice`) | **معطّل** | مراجعة `pushState` و`devices` + نشر بموافقة منفصلة |
| `reconcileDeliveryStatuses` / `deliveryWebhook` | **معطّلة** | عقد webhook + mapping مُثبت (Stage 8 مسبقاً) |
| التقارير والقراءة | تُفتح أولاً (بلا كتابات) | مباشرة بعد P4 مع تقييد الكتابة |

**لم يُفعَّل أي جزء من هذا الوضع في هذه الجولة — هو تعريف لخطة مستقبلية فقط.**

## 6. Click — تسوية بعد الكارثة (بدون إعادة إرسال)

1. استخراج قائمة كل طلب `dispatchState ≠ idle` من البيانات المستعادة (وإن كانت فارغة فهذا مكسب، لا افتراض).
2. لكل طلب: مقارنة **قراءة فقط** مع سجل المزوّد (عند توفر عقد الاستجابة و`getorder` — حالياً محجوب على D4/D7/D9/D10). **ممنوع `setorder` للتسوية.**
3. ثلاث نتائج ممكنة فقط: (أ) شحنة موجودة لدى المزوّد → تُوثَّق ويُصلح رقم التتبع بشرياً بموافقة؛ (ب) لا شحنة → يبقى الطلب بحالة مراجعة؛ (ج) غير محسوم → يبقى محجوباً حتى حسم الحالة.
4. التوقيع البشري مطلوب لكل قرار؛ يُسجَّل في سجل الحادث (من، متى، ماذا قرر، بناءً على أي دليل).

---

## 7. FCM — منع الإشعارات المكررة

1. لا تفعّل الدفع قبل مراجعة كل `notices` بحالة `pushState ∈ {pending, processing, sending}`؛ إما تُعتمد (لا إرسال) أو تُصفَّر بحالة موثقة.
2. الإشعارات القديمة باقية كسجل داخلي (`notices`) ولا تُعيد الإرسال بطبيعتها — الخطر فقط منعطفات المزامنة.
3. `devices`: تُعامل كغير موثوقة؛ إعادة تسجيل الأجهزة بإذن مستخدميها.
4. `pushNotice` حالياً غير منشورة — يبقى كذلك حتى قرار تفعيل مستقل.

## 8. مسارات الأصول غير المغطاة بـFirestore

| الأصل | المسار |
|---|---|
| **Firebase Auth** | `firebase auth:export` دوري (بموافقة) إلى خزنة المالك؛ عند الاستعادة: مطابقة UID↔members؛ إعادة تعيين كلمة مرور/إرسال روابط استعادة عند الاقتضاء. لا تنزيل hash/password data إلى جهاز غير معتمد |
| **KMS** | التحقق أن المفتاح/الإصدار المذكور في `VELNIX_KMS_KEY` ما زال READY وقابل للفك؛ إن كان بتدمير مجدول → إيقافه فوراً؛ فقدان المفتاح = إعادة إدخال أسرار الشركات يدوياً |
| **GCS** | لا بيانات تطبيقية الآن؛ لو أُضيفت، سياسة نسخ منفصلة (lifecycle + نسخ موثقة) |
| **IAM/قواعد/Env** | تُستعاد من Git + Release Manifest؛ `ALLOWED_DELIVERY_HOSTS` و`VELNIX_KMS_KEY` تُراجع قيمهما قبل عودة الخدمة |
| **App Check / OAuth / FCM إعدادات** | مراجعة الحالة في Console كبند بخروج وثيق من الحادث |

| الدور | المالك المقترح | المهام |

## 11. المخاطر والتكاليف لكل خطوة (منهجية)

| الخطوة | المخاطرة | التكلفة (منهجية — بلا أرقام مخترعة) |
|---|---|---|
| استرجاع معزول | خطأ في الأعلام يوجّه الاسترجاع للخطأ | عمليات قراءة/كتابة وفق التسعيرة + زمن بشري |
| استعادة إنتاجية | فقدان الفارق بعد النقطة | تكلفة العملية + تكلفة مراجعة الفارق |
| PITR snapshot-export | نافذة 7 أيام فقط | تسعيرة PITR + قراءات التصدير |
| تسوية Click | قرار مالي خاطئ | زمن مراجعة بشري — لا مكالمات مدفوعة متوقعة |

> الأرقام النهائية لا تُقدَّر من الذاكرة — تُحسب من التسعيرة الرسمية وقت القرار.

---

## 12. العودة (Rollback) عن الاستعادة نفسها

- الاستعادة نفشل/ناتج غير صحيح؟ **لا تُعاد محاولة تراكمية على قاعدة حية** — تُنتقل إلى نقطة أخرى بنفس مسار P1 (معزول أولاً)، بعد تأكيد P0 مجدداً.
- لا تُعالج أبداً بحذف مستندات أو تصفير أقفال يدوياً خارج مسار موثق بموافقة.

## 13. تحقق نهائي
