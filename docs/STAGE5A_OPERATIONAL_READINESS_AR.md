تاريخ المراجعة:14أكتوبر2026. المصدر المعتمد `e35c973b7251d30b4c0b7e52eb7036db934b7f6f`، الفرع `audit/production-readiness`؛ checkout نظيف ومتطابق مع remote عند البداية. لم يتغير كود التطبيق أو Backend في5A، ولم تنفذ اتصالات Click أو عمليات Firebase فعلية أو نشر أو إنشاء موارد/فوترة أو Merge. تغييرات5A وثائق وخطة قبول فقط.

## ما ثبت وما لم يثبت

راجعنا تقارير المرحلة الرابعة وإغلاق CI، خطة قبول Staging، تهيئة المشروع الحالي، مصفوفة الصلاحيات، عقد Click ومصادره وكود المحول والحظر. لم نعد التدقيق السابق. أكد المالك خارج Codex نجاح Push وPR على e35c973، وجميع وظائف Firebase وFlutter وAndroid. لم يزوّد أرقام التشغيل؛ [فحوص النسخة](https://github.com/Mode2094/velnix/commit/e35c973b7251d30b4c0b7e52eb7036db934b7f6f/checks)، [Actions](https://github.com/Mode2094/velnix/actions)، [PR#1](https://github.com/Mode2094/velnix/pull/1). هذا تأكيد المالك، وليس قراءة API محلية. المحاولة الحالية إلى API تنتهي CONNECT403 من proxy قبل وصول HTTP إلى GitHub؛ Git read يعمل. لا يثبت هذا عيباً في Velnix أو نقص صلاحية token، ولا يستدعي طلب PAT في المحادثة.

فحوص5A الحالية:4 اختبارات Flutter لتهيئة Firebase،58 Node،48 Auth/Firestore على loopback،7 إعداد Firebase و5 إعداد runtime في Python؛ جميعها ناجحة دون تخطي في Node/المحاكيات. فحص توقيعات الأسرار345 ملفاً بلا نتائج، وAndroid/iOS preflight ناجحان. Web preflight فاشل لغياب site key، ولم يتجاوز. لم نكرر بناء Web/Android الذي أكد CI نجاحه، ولم نبن iOS. لم يظهر عيب برمجي جديد يستدعي إصلاحاً؛ صُححت تعليمات تشغيل قديمة توحي بعزل Staging وبنسخ/استعادة على مشروع آخر غير معتمد.

## ترتيب مراجعة Console قبل أي تعديل

1. **Project settings / General:** تأكيد المشروع velnix-6c1a2 وثلاثة التسجيلات الحالية فقط، خصوصاً Web النشط وليس قيد الحذف؛ مطابقة package/bundle/App IDs. تسجيل نوع خطة الفوترة الحالية دون تغييرها.
2. **Authentication:** قراءة providers وAuthorized Domains وإعداد OAuth عند الحاجة؛ التأكد من وجود هوية مدير عام مخولة وعضويتها. إن كانت الحسابات/العضويات ناقصة، نعد قائمة إنشاء اصطناعية ونطلب تفويضاً محدداً قبل الإنشاء أو bootstrap؛ لا ننفذه أثناء5A.
3. **Firestore:** قراءة قاعدة default وموقعها وقواعدها والفهارس الحالية. عدد الفهارس في المصدر109 لا يثبت عدد الفهارس المنشورة أو جاهزيتها. لا إنشاء قاعدة ولا استيراد/مسح/تعديل بيانات.
4. **Functions / Cloud Run:** جرد موجود فقط: اسم/region/revision/حالة/هوية كل خدمة، ومطابقة europe-west1. إن كان Backend غير منشور فلا تعمل الرحلة الحقيقية؛ نبلغ عن النقص. نشر Functions v2 لاحقاً قد يتطلب Blaze وخدمات مدفوعة، فلا نستبدله باتصال Firestore مباشر ولا نفعّل فوترة لتجاوزه.
5. **App Check:** مراجعة التسجيل وenforcement والمقاييس دون تغيير؛ المزود الحالي Play Integrity لـAndroid وDeviceCheck لـiOS وreCAPTCHA v3 لـWeb. توفير site key العام وdomains، وشهادات Android ومتطلبات التوزيع وApple. لا تعطيل enforcement ولا debug provider في release لتجاوز الرفض. تأكيد رفض callable بلا App Check يتطلب طلباً فعلياً مخولاً لاحقاً، لا استدعاء handler محلياً.
6. **FCM:** قراءة إعداد Cloud Messaging؛ عند تفويض اختبار الإشعارات نجهز VAPID العام وWorker المطابق وAPNs والصلاحيات. لا تعرض device tokens أو مفاتيح APNs. لا نفعّل Google/Push flags قبل تحقق إعداداتهما.
7. **IAM/KMS:** جرد runtime identity والـbindings الحالية مع مالك مخول؛ قارن احتياجات Firestore/Auth/FCM بالأدوار المرشحة في config/iam.staging.example.json دون تطبيق policy أو منح Owner/Editor. مفتاح KMS وموقعه وencrypt/decrypt على المفتاح فقط مطلوبان قبل اعتماد شركة، مع فصل deploy/backup/runtime. إن كان غير موجود يبقى مؤجلاً حتى تفويض إنشاء/تكلفة منفصل.

يمكن أتمتة هذه القراءات عبر APIs الرسمية بعد إتاحة اتصال وهوية read-only مناسبة، دون secrets في التقرير؛ لا توجد هوية Google مخولة حالياً هنا. UI إعدادات التسجيل/المزودات والحسابات والشهادات يحتاج المالك أو مشغلاً مفوضاً. أي نقص يستدعي تغييراً يُعرض كتغيير محدد للموافقة أولاً، وليس إذناً عاماً من هذه الخطة.

## خطة5B الداخلية للأدوار الخمسة

تحتاج أولاً موافقة على استخدام المشروع المشترك، وخمسة حسابات اصطناعية بأدوار معروفة، وفريقين مستقلين لاختبار الرفض، وحساب غير نشط/بلا عضوية. جهّز عيّنات مالك/زميل فريق/فريق آخر من بيانات اصطناعية فقط، ودوّن معرفاتها خارج التقرير العام. لا تستعمل بيانات عميل أو أرقام هاتف حقيقية ولا حذف نهائي أو اختبارات الحمل/المسح. لا تمنح تفويضات إضافية لمجرد إنجاح سيناريو. المرجع [مصفوفة الصلاحيات](ROLE_PERMISSION_MATRIX.md) وfunctions/src/policy.js.

| الدور | الإنشاء والرؤية المطلوبان | التعديل/الحالة والتفويض المطلوب إثباتهما |
|---|---|---|
| مدير عام generalManager | إنشاء ورؤية الجميع؛ المبالغ بصلاحياته | إدارة الأعضاء والإعدادات ودورة داخلية مشروعة؛ رفض الانتقال غير الصالح وحماية آخر مدير نشط |
| مدير manager | إنشاء؛ افتراضياً ملكه فقط | تعديل ملكه في created/review؛ تغيير الحالة/رؤية الجميع/التقارير بحسب التفويض الصريح فقط؛ منع منح صلاحيات تتجاوز سلطته |
| مستودع warehouse | إنشاء ورؤية الجميع؛ مبالغ الغير محجوبة دون viewAmounts | تغيير الحالة ضمن الانتقالات المسموحة؛ رؤية الجميع لا تعني تعديل الجميع أو إرسال شحنة |
| مبيعات sales | إنشاء ورؤية ملكه ومدخلي بيانات فريقه الحالي فقط | تعديل ملكه في created/review؛ رفض نطاق فريق آخر، وسحب رؤية الفريق فور انتقال العضو؛ تغيير الحالة يحتاج تفويضاً |
| مدخل بيانات dataEntry | إنشاء ورؤية ملكه فقط | تعديل ملكه في created/review؛ رفض طلبات الغير وتغيير الحالة دون تفويض |

التفويض viewAllOrders/viewAmounts/editAllOrders/updateOrderStatus/sendToDelivery مستقل؛ يُثبت قبل كل حالة قبول ولا يستنتج من اسم الدور. المالك يرى مبالغ طلبه؛ viewAmounts يسمح بمبالغ الغير داخل نطاق القراءة فقط.

تكرر الرحلة التالية لكل دور، مع توثيق PASS/FAIL/BLOCKED وSHA والمنصة ووقت الاختبار ومعرف عينة وسجل audit منقح:

- **R1:** دخول حساب نشط وإنشاء طلب اصطناعي وظهوره مع حدث إنشاء واحد؛ رفض حساب غير نشط أو بلا عضوية؛ double tap/إعادة المحاولة لا تنشئ طلبين.
- **R2:** قوائم وبحث وتفاصيل وإحصائيات ضمن نطاق الدور، ثم محاولة معرف خارج نطاقه؛ لا تسرب بيانات/مبالغ في التقارير أو المستند. لا طباعة جهاز في5A.
- **R3:** تعديل مسموح ورفض غير المسموح، وتعارض تعديلين لا يفقد تحديثاً. النقل بين الفرق يسحب الرؤية السابقة؛ تعطيل العضو يسحب الوصول.
- **R4:** created→review→preparing→ready→delivered ينفذه صاحب الصلاحية فقط؛ completionSource=internal وactor/time/audit. رفض إكمال طلب شركة أو sending/sent/needs_review، ورفض إعادة فتح النهائي وتزوير الحالات الخارجية. لا يتطلب هذا إرسال Click.
- **R5:** لا حذف نهائي لأي دور ولا كتابة مباشرة للمجموعات المحمية عبر SDK. فحص الرفض يكون بعملية محدودة معتمدة على عينة اصطناعية فقط؛ لا حذف بيانات أو استخدام removeorder. لا يحذف سجل التدقيق أو يعدل من العميل.
- **R6:** إشعارات داخل التطبيق ضمن النطاق مع الحفاظ على read state؛ FCM بعد بوابته فقط: سماح/رفض، foreground/background/open، تعطيل ونقل فريق وخروج أثناء انقطاع الشبكة. إثبات عدم وصول بيانات لاحقاً يحتاج جهازاً فعلياً؛ Mock لا يغلقه.
- **R7:** سجل تدقيق للأفعال المسموحة ونتائج الرفض الآمنة؛ لا أسرار شركة أو tokens أو بيانات شخصية غير لازمة في logs. إخفاء viewAudit عن غير المخول لا يكفي دون رفض backend.

اختبارات المحاكيات تعطي أدلة على هذه السياسات محلياً، لكنها تستدعي handlers وقواعد على loopback؛ ليست اختبار callable منشور أو App Check أو IAM الحقيقي.

## Click وتطبيق الشركة

الموجود: getorder POST إلى /Client/getorder وOrder_ID/User_Name/User_Pass وAuthorization: client موثقة بالطلبات؛ response غير موثق. setorder له أسماء12 حقلاً في النص، لكن HTTP method وشكل نجاح/فشل والعلاقة بين Client_Serial/Order_ID/tracking غير مؤكدة. removeorder ليس مسار حذف داخلي، ولا حاجة لتنفيذه لقبول التطبيق. مصادر كل حقل في [تقرير التوافق](CLICK_DELIVERY_COMPATIBILITY_AR.md) و[أسئلة الشركة](CLICK_DELIVERY_QUESTIONS_AR.md).

المطلوب من الشركة: sandbox baseURL وحدوده، إثبات أن حساب الاختبار تاجر وله API permission وليس مستخدم تطبيق فقط، طريقة المصادقة الصالحة، طلب/استجابة نجاح وفشل منزوعة الأسرار لـsetorder/getorder، أكواد الحالات السبع وترتيبها/توقيتها، idempotency والاستعلام عن إنشاء ملتبس، الأنواع/الوحدات/العملة وOrd_Amt ورسوم التسليم والإلغاء والتحصيل والجزئي والمرتجع. لا endpoint webhook مفترض ولا مبالغ محسوبة من التخمين. الحالات المطلوبة: قيد انتظار الموافقة، مخزن الشحن، في الشحن، تم التسليم، تسليم جزئي، مؤجل، ملغي. تسمياتها الداخلية ليست أكواد API رسمية؛ نحتاج مثال استجابة لكل حالة، ولا تسقط حالات خارجية غير معروفة إلى delivered أو cancelled.

قال المالك إن لديه رابط التطبيق الرسمي وحساب اختبار، لكن الرابط المحدد وإثبات صلاحيات API غير متاحين ضمن هذه المراجعة. نحتاج رابط المتجر الرسمي وpackage ID/نسخة/متطلبات النظام لتقييمه؛ لا ننزل APK من مصدر غير موثق. فحص واجهة تطبيق Click مستقل عن ترخيص API ولا يثبت العقد. Android SDK وadb موجودان هنا، لكن emulator/system images و/dev/kvm غير متاحة حالياً؛ إمكان بناء Velnix لا يعني توفر محاكي تفاعلي. جهاز Android اختباري مع Google Play قد يكون المسار العملي، مع تأكيد الشركة دعم المحاكي/قيود Integrity قبل تجهيز صورة مناسبة. لا دخول أو إنشاء شحنات في5A.

اعتماد الاختبار يُدخل لاحقاً عبر وسيلة أسرار آمنة معتمدة إلى Backend فقط، ثم يخزن وفق KMS عند تفويض ذلك؛ لا يُطلب في المحادثة أو Dart defines أو Git. لا تعاد استخدام بيانات الأمثلة أو المحادثات السابقة. الحساب وحده لا يبرر رفع حظر المحول. إكمال adapter بعد وصول العقد يحتاج مهمة مفوضة واختبارات قبل أي اتصال؛ getorder حتى HTTP200 في Mock لا يعتبر نجاح أعمال. generic_v1 محظور كبديل.

## البناء والتكلفة وتقسيم المسؤولية

- يمكننا تلقائياً: مراجعة تطابق الملفات العامة وpreflight، اختبارات Flutter/Node/المحاكيات وMock، بناء Web/Android محلياً عند اكتمال الإعداد، وتجهيز Worker بعد VAPID العام. لا حاجة لإعادة الأبنية التي أكد CI نجاحها لمجرد تغيير الوثائق.
- Android: debug build السابق وCI مثبتان، أما توزيع release فيحتاج keystore خاصاً وتوقيعاً وSHA للنسخة الموقعة عبر خزنة آمنة، لا افتراض إعداد signing الموجود. لا Google Play الآن.
- iOS: يحتاج Mac/Xcode متوافقاً وApple Team وشهادة/provisioning مطابقين للـbundle، وقدرات/APNs عند الإشعارات. لم يُبن iOS في هذه البيئة ولا يعتبر ناجحاً.
- Web: يتوقف Live startup على site key المذكور؛ HTTPS/Authorized Domains وPush Worker/VAPID عند اختبار FCM. نجاح compile لا يثبت startup أو Auth/AppCheck.
- دون تفعيل خدمات: المراجعة والأدوات والمحاكيات محلياً لا تنشئ كلفة Firebase. الاستعمال الحقيقي قد يستهلك حصص الخدمات الحالية؛ لا نضمن صفراً. Functions v2 وKMS والجدولة والنسخ السحابي وأي حصص متجاوزة قد تتطلب فوترة؛ Apple signing/أجهزة/حسابات توزيع قد تتطلب اشتراكات/تكلفة حسب ما يملكه المالك. لا أسعار مفترضة ولا تفعيل Blaze أو موارد مدفوعة. إن احتاج المسار خدمة غير متاحة على الخطة الحالية يبقى BLOCKED لحين قرار محدد.

## قائمة ما يجهزه المالك والخطوة الأولى

1. أول موافقة مطلوبة: **وصول قراءة فقط للمشروع velnix-6c1a2 لجرد الخدمات والتسجيلات والفهارس وIAM دون تغييرات**، أو يزود المالك نتائج Console المنقحة بنفسه. لا تشمل هذه الموافقة إنشاء حسابات أو نشر/فوترة أو تعديل بيانات. يمكن إرسال المعرفات العامة وحالة الخدمات؛ لا لقطات تحمل أسراراً.
2. تأكيد Web النشط + مفتاح reCAPTCHA v3 العام وdomains، وقائمة الخدمات المنشورة وحالتها/region/identity وخطة الفوترة الحالية؛ لا نطلب أي private key.
3. بعد الجرد: موافقة منفصلة على قائمة الحسابات/العضويات/الطلبات الاصطناعية المحدودة ومن سينفذها، وعلى أي إعداد ناقص بعد عرضه تفصيلياً. إذا كان Backend غير موجود أو يتطلب Blaze يبقى الاختبار متوقفاً دون تفعيل تلقائي.
4. أجهزة Android وiOS/Mac ومتصفحات مستهدفة، ومسؤول توقيع/APNs وأسرار التوقيع خارج Git؛ لا مراجعة تطبيق من المالك مطلوبة الآن ولا اختبار طابعة في5A.
