# تشغيل ومتابعة Velnix

البيئة المحلية: source scripts/cloud-env.sh ثم scripts/validate.sh. لا تستخدم الإنتاج للفحوص. النتائج والقيود في TEST_RESULTS. سجل التقدم في Git والوثائق؛ الفرع audit/production-readiness، لا push أو deploy تلقائي.

للموظف: دخول بحساب مفعّل، إنشاء طلب، مراجعة البيانات، متابعة الحالة، اختيار المرشحات، طباعة من التفاصيل. المدير ينشئ/يعدل الموظفين ويراجع الدور والصلاحيات والفريق ثم الحفظ؛ إيقاف الموظف يسحب الوصول بعد تحديث الملف وتحقق الخادم. Google وحده لا ينشئ موظفاً مخولاً.

المشغل يراجع إعدادات المؤسسة والهاتف وذيل المستند، والشركة وعقد adapter وخرائط الحالة. اختبر الاتصال قبل التفعيل. إرسال ملتبس لا يعاد تلقائياً: افحص سجل المزود والتتبع أولاً ثم إجراء المراجعة المخول. الأرشفة تحفظ التاريخ ولا توقف استقبال حالة الشحنة القديمة.

قبل نشر مخول: انسخ بيانات staging إلى مجموعة اختبار خالية من بيانات حقيقية، انشر فهارس/قواعد/Functions بعد مراجعتها، انتظر جاهزية الفهارس، وشغّل دورة تطبيق حقيقية. اختبر أخطاء Auth/App Check والشركة وFCM والطباعة، وراقب latency/errors وعدد قراءات Firestore وتكاليف KMS.

النسخ والاستعادة: يحدد المالك RPO/RTO والمنطقة وسياسة الاحتفاظ. جهّز Firestore managed export/backup في bucket آمن مع IAM وأسماء وتواريخ واضحة، ونسخ إعدادات قواعد/فهارس وإصدارات Functions ومرجع KMS دون استخراج مفتاح. جرّب restore إلى مشروع staging منفصل ثم تحقق عدد المستندات وعينات الطلبات وسجلاتها والصلاحيات. لا تستورد فوق إنتاج قائم دون إذن وخطة رجوع. حسابات Auth وإعداد OAuth وKMS ليست مشمولة تلقائياً في Firestore export ويجب تخطيط استعادتها منفصلة.

Rollback: احتفظ بالنسخة السابقة والـlockfiles والقواعد والفهارس المتوافقة ومخطط البيانات، أوقف عمليات إرسال جديدة إذا ظهرت حالات ملتبسة، ولا تعد إرسال شحنات كجزء من rollback. هذه خطة مقترحة غير منفذة على مشروع خارجي، وتحتاج تجربة استعادة فعلية قبل الاعتماد.
