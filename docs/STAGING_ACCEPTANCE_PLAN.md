# خطة قبول المرحلة الخامسة — Firebase وClick والأجهزة

> تحديث طلب المالك الحالي: التجربة والتسليم النهائي على مشروع واحد velnix-6c1a2. [وثيقة ربط المشروع الحالي](FIREBASE_CURRENT_PROJECT_SETUP_AR.md) تحدد التسجيلات والإعدادات المحلية والقيود. افتراض مشروع Staging مستقل في الخطط السابقة أُلغي بهذا الطلب؛ قيمة staging الآن لا تثبت عزل البيانات، ولا تسمح بتشغيل اختبارات المسح أو الاستعادة على المشروع الحقيقي. لا إنشاء موارد أو فوترة أو Deploy في هذا الطلب.

هذه خطة مستقبلية وليست إذن نشر. لم تُنشأ موارد ولم ينفذ Deploy أو Merge أو اتصال بالشركة. تعتمد مشروع Firebase الواحد velnix-6c1a2 وفق طلب المالك الحالي؛ بيانات الاختبار اصطناعية ولا توجد عزلة مشروع منفصل؛ تفعيل الفوترة أو النشر التجريبي يحتاج موافقة المالك المحددة مسبقاً. [تقرير المرحلة الرابعة](SAFE_HANDOFF_STAGE4_REPORT_AR.md) يبين الأدلة المحلية وحدودها.

## بوابات البدء

| البوابة | ما يوفره أو يعتمده المالك | معيار الاجتياز |
|---|---|---|
| مشروع Firebase الحالي | التسجيلات المعتمدة للمشروع velnix-6c1a2، صلاحيات مشغل، Functions europe-west1 | تأكيد الخدمات الموجودة وعدم استعمال بيانات حقيقية أو تشغيل wipe/import؛ أي تعديل سحابي يحتاج تفويضاً |
| إعداد العميل والمنصات | معرفات Firebase العامة، Authorized Domains، OAuth/SHA، ملفات المنصات والتوقيع عبر وسيلة آمنة | preflight مستقل لكل منصة ومشروع ثم دخول على أجهزة فعلية |
| هوية التشغيل وKMS لاحقاً | مراجعة هوية Backend الموجود؛ KMS عند اختبار الاعتمادات فقط وبتفويض منفصل | لا Owner/Editor؛ تجربة تشفير وفك ومنع هوية غير مخولة، دون عرض ciphertext أو أسرار |
| Click الرسمي | استجابات منزوعة الأسرار وأكواد الحالات والعلاقة بين المعرفات والمعاني المالية وحساب sandbox | مراجعة العقد وإكمال واختبار Adapter بمهمة مفوضة قبل تفعيله |
| الأجهزة والإشعارات والطباعة | أجهزة ومتصفحات مستهدفة، Mac/Xcode/APNs، طراز الطابعة والماسح والدقة | أدلة فعلية لكل منصة وطراز؛ نجاح Mock أو PDF ليس قبول جهاز |
| التشغيل والاستعادة | أهداف p95 والكلفة وRPO/RTO والاحتفاظ والمسؤول عن الإرسال الملتبس | تجربة الاستعادة المعزولة ونتيجة مقابل أهداف المالك |

يمكن بدء قبول Firebase الداخلي بعد بواباته دون انتظار Click، لكن لا يمكن إغلاق المرحلة الخامسة كاملة دون الشركة والأجهزة ومراجعة المالك. لا تُرسل كلمات المرور أو tokens أو مفاتيح التوقيع أو service-account JSON في المحادثة أو Git.

## تهيئة مستقبلية بعد التفويض فقط

1. راجع [التهيئة وتسليم المصدر](SAFE_CONFIGURATION_HANDOFF_AR.md). املأ نسخة محلية مستثناة من مثال Staging لكل منصة، وفحّصها offline مع project ID معتمد صراحة. Google وPush يبقيان معطلين حتى تهيئتهما. أبنية Demo تخص QA فقط.
2. سجّل Auth Email/Password وGoogle حسب النطاق المتفق عليه. نفذ bootstrap لأول مدير عام فقط بواسطة مشغل مخول ومع تأكيد المشروع، ثم حسابات اصطناعية مستقلة للأدوار الخمسة؛ Google لا يمنح عضوية بمجرد تسجيل الدخول.
3. راجع القواعد والفهارس الـ109 ثم انشر إلى المشروع الحالي فقط بعد موافقة لاحقة صريحة على النشر ومتطلباته المالية، وانتظر READY. محاكي Firestore لا يثبت جاهزية الفهارس أو IAM الحقيقي.
4. راجع حساب التشغيل وKMS وFCM وApp Check. رفض callable بلا App Check يجب إثباته فعلياً، لا عبر Functions.run. استخدم Play Integrity وDeviceCheck وreCAPTCHA v3 حسب المنصة؛ debug tokens محصورة في debug Staging وممنوعة في release والإنتاج.
5. جهز Web Push Service Worker من scripts/configure_web_push.py وVAPID العام عند تفعيل Push؛ تحقق من تطابق مشروع Worker والتطبيق. iOS يحتاج قدرات Push وAPNs وURL schemes وتهيئة المنصة الرسمية؛ ليس جاهزاً بمجرد بناء Dart.
6. راجع الوجهات المطلوبة بعد تحديد المشروع: endpoint Functions التجريبي، خدمات Firebase/Auth/App Check/KMS/FCM/Google المستعملة. لا تضف wildcard أو host شركة قبل اعتماد sandbox. حافظ على TLS؛ تأكد من عمل SDK/gRPC فعلياً.

## حظر Click — شرط مستقل لا يجوز تجاوزه

`click_delivery_v1` غير مفعل. لا تستعمل `generic_v1` باعتباره متوافقاً مع Click، ولا تغيّر provider للتحايل على الحظر. لا تفترض `/health` أو Bearer أو `/orders` أو webhook/HMAC أو polling contract لشركة Click. وجود getorder في الوثائق لا يثبت شكل الاستجابة أو نجاح الشحنة، وsetorder وremoveorder غير منفذين فعلياً. لا يستخدم removeorder لحذف داخلي.

المصدر الملزم هو [توافق Click ومصادر الحقول](CLICK_DELIVERY_COMPATIBILITY_AR.md) و[أسئلة الشركة](CLICK_DELIVERY_QUESTIONS_AR.md). يلزم قبل الاتصال: الطرق والمسارات الرسمية، المصادقة والقيود، نماذج نجاح وفشل create/query، الأكواد والانتقالات السبعة، الوقت وترتيب التحديثات، Client_Serial وOrder_ID والتتبع، idempotency وإعادة المحاولة، OrdAmt والعملة والتحصيل والمرتجع ورسوم الإلغاء والتوصيل. يجب توضيح هل يوجد webhook أصلاً؛ إذا لم يوثق فلا ينشأ أو يفترض.

بعد استلام العقد وإكمال المحول واختباراته وموافقة sandbox فقط، تجري الشركة اختبارات تعاونية بشحنات تجريبية مرخصة. أي response غير مؤكد أو HTTP200 غير موثق يبقى فشلاً/غير معروف، لا نجاحاً. لا حسابات مالية ولا مبالغ جزئية من تخمين. حالات الشحن الخارجية منفصلة عن إعداد الطلب الداخلي؛ العرض الحالي لا يثبت مزامنتها الفعلية.

## قائمة قبول نهائية

|---|---|---|
| Firebase/Auth | دخول وخروج واستعادة، حساب غير نشط أو بلا عضوية، تعطيل أثناء الجلسة، Google على المنصات المتفق عليها | منصة ودور ونتيجة منزوعة الأسرار |
| الصلاحيات والخصوصية | جميع الأدوار تنشئ؛ منع حذف نهائي؛ نطاق الفرق؛ إخفاء المبالغ في قوائم/تقارير/PDF؛ رفض Firestore المباشر؛ تعارض آخر مدير | assertions وسجل تدقيق دون بيانات عميل |
| App Check/IAM/KMS | رفض غير موثق، إصدار release بمزود فعلي، أقل صلاحيات، تشفير/فك بأذونات صحيحة ورفض المخالف | سجلات codes آمنة ومراجعة IAM مستقلة |
| دورة الطلب الداخلية | created→review→preparing→ready→delivered، مصدر internal، منع إعادة فتح نهائي وإكمال شحنة شركة | أحداث الطلب وaudit |
| Click المشروط | إنشاء واحد وتطابق المعرفات، الحالات السبع الرسمية، التأجيل والتحديث المتأخر/المكرر، الجزئي والإلغاء حسب مبلغ موثق | تطابق سجل sandbox مع التطبيق والعقد الرسمي |
| انقطاع الشركة | timeout قبل/بعد الإرسال، needs_review عند الالتباس، منع إعادة إنشاء تلقائية، رد مشوه/429/5xx | إثبات عدم تضاعف الشحنة وعدم اختلاق مبلغ |
| المزامنة | اختبارات query حسب العقد؛ webhook فقط إذا وثق لاحقاً؛ منع التراجع والتكرار | سجل الأحداث وربط الطلب الصحيح |

| الواجهات والأجهزة | رحلة الأدوار الخمسة، RTL، عشرة عروض و200%، انقطاع وempty/error، Android/iOS ومتصفحات | نتائج جهاز فعلية ومراجعة المالك لاحقاً |
| البناء والتوقيع | Web HTTPS، Android موقّع بإعداد تجريبي مستقل، iOS على Mac/Xcode مع capabilities | artifact مرتبط بـSHA وبيئة ومنصة وتوقيع صحيح |

## حدود التشغيل ومعيار القرار

push الحالي أربع محاولات، lease دقيقتان، استعادة بجدول15 دقيقة،25 حالة وميزانية45 ثانية. لا ضمان exactly-once عبر FCM والحفظ؛ acknowledgements وnoticeId تقللان التكرار. إذا فشل إلغاء تسجيل الجهاز وحذف token معاً، الخروج المحلي لا يثبت سحب الإشعارات؛ اختبار الجهاز والإجراءات التشغيلية شرط قبول.

poll الحالي100 شحنة في الدورة، لا100 شركة. هذه حدود الكود ولا تثبت قدرة Click على المزامنة؛ المحول محجوب. لا إعادة إرسال شحنة ملتبسة لتجاوز timeout. لا scheduler أو خدمة مدفوعة جديدة.

تحتاج بوابات القبول أدلة باسم SHA والمنصة/المشروع والنتيجة والمالك المراجع دون أسرار. أي تسرب نطاق أو مبلغ، تضاعف شحنة، عقد Click ناقص، فشل جهاز، أو استعادة غير مجربة يمنع إغلاق المرحلة الخامسة. نجاح CI يثبت فحوص المصدر ولا يمنح تصريح إنتاج أو Merge/Deploy.
