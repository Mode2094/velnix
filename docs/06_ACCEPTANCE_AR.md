# معايير قبول المرحلة الأولى (للتطوير المستقبلي)

**ملحوظة:** هذه القائمة معايير اختبار مستهدفة، وليست إقراراً بأن النسخة التجريبية تحقق التكاملات الحقيقية.

- [ ] يتم الدخول بأمان بهوية Firebase مسجلة ومفعلة.
- [ ] يستطيع كل دور من الأدوار الخمسة إنشاء طلب جديد.
- [ ] يستطيع المدير العام إدارة جميع المستخدمين والشركات والطلبات.
- [ ] صلاحيات المدير ليست كلية تلقائياً، بل مقيدة بإعدادات صريحة.
- [ ] مبيعات يشاهد طلباته وطلبات مدخلي البيانات في النطاق المتفق.
- [ ] مدخل البيانات يرى طلباته فقط ويتعذر عليه قراءة طلب غير مسموح عبر Firestore المباشر.
- [ ] موظف المستودع يتعامل مع حالة وتجهيز الطلب ولا يوجد نظام مخزون.
- [ ] لا توجد وظيفة حذف نهائي للطلب في الواجهة أو واجهات العميل.
- [ ] إلغاء الطلب وحالات الإكمال محفوظة ضمن سجل تدقيق لا يُمسح.
- [ ] إرسال الطلب إلى الشركة الأولى يعطي رقم شحنة أو خطأ موثق، بلا تكرار للشحنات.
- [ ] لا تنكشف مفاتيح شركة التوصيل في العميل أو سجل التتبع أو Firestore.
- [ ] وصول Webhook / Polling بالـstatus الفعلي يغير الحالة الداخلية الصحيحة ويضيف event؛ لا يعيد حالة قديمة.
- [ ] الإشعارات تصل للمستخدمين ذوي الصلاحيات الصحيحة ولا تسرب بيانات العملاء.
- [ ] Offline / Network errors تظهر رسائل واضحة ويمكن إعادة المحاولة.
- [ ] لا تظهر أقسام المتجر والمخزون أو مدفوعات التجارة الإلكترونية.
- [ ] Android/iOS/Web تُراجع فقط حسب منصات العميل المتفق عليها.
- [ ] اجتياز `flutter analyze`, `flutter test` واختبارات وظائف Cloud Functions وFirestore emulator قبل التسليم.
