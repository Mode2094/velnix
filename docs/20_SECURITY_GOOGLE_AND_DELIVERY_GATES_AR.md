# Velnix — بوابات الأمان والتكامل قبل الإنتاج

## 1) دخول Gmail / حساب Google (غير منفذ الآن)

- المصادقة الحالية: Firebase Authentication بالبريد وكلمة المرور، مع رابط استعادة كلمة المرور أضيف v0.6.
- الدخول بجوجل يحتاج تفعيل Google provider من Firebase Auth؛ إعداد نطاق Web / Authorized Domains، وOAuth client IDs؛ Android SHA-1 وSHA-256 وإعداد google-services؛ Apple URL Scheme وملفات التهيئة. لا تضف زر Google قبل عمله على Android وiOS والويب فعلياً.
- **أهم قاعدة أمان:** نجاح Google OAuth لا يمنح دور موظف تلقائياً. يجب أن تطابق هوية Firebase UID عضواً محدداً ومفعلاً في `members/{uid}`، وأن تتأكد من ربط هوية Google بحساب الموظف الصحيح بشكل متحكم به. لا تقبل أي Gmail جديد لمجرد نجاح تسجيل Google ولا تمنحه دوراً افتراضياً.
- يجب تغطية: حساب موظف موجود بالبريد وكلمة المرور ثم يريد ربط Google، تطابق البريد مع اختلاف UID، منع الاستيلاء عن طريق البريد فقط، حساب غير مفعل، إلغاء الموظف أثناء الجلسة، إعادة المصادقة للحساسة.
- التوصية: تنفيذ الربط الآمن للحسابات (Account Linking) مع إعادة إثبات هوية صاحب الحساب، ثم Google Sign-In عبر `google_sign_in` native وFirebase popup للويب. لا ينفذ «auto-create member» في العميل.

المراجع: https://firebase.google.com/docs/auth/flutter/federated-auth و https://firebase.google.com/docs/auth/flutter/manage-users

## 2) Firebase وقواعد Firestore

- تقفل القواعد الموجودة كل قراءة/كتابة إلى الطلبات والشركات والأسرار مباشرة من العميل، وتسمح بقراءة الملف الشخصي للمستخدم ذاته فقط. خادم Admin SDK **يتجاوز قواعد Firestore**؛ لذلك كل Callable يجب أن تتحقق من عضوية المستخدم والصلاحيات ومصدر الطلب قبل التنفيذ.
- اختبر القواعد باستخدام Emulator لـ: زائر مجهول / مدخل بيانات / مبيعات / مستودع / مدير / مدير عام؛ منع قراءة سر API أو الطلب عبر Firestore client، حتى لو عرف المستخدم المعرّف.
- يجب تفعيل App Check على جميع المنصات قبل الإنتاج؛ Debug tokens للمحاكي فقط، مع اختبار Play Integrity / Apple Device Check / Web CAPTCHA وإيقاف تجاوزات التصحيح في الإصدار التجاري.
- Cloud Functions تحتاج حساب خدمة بأقل صلاحيات، وKMS لصلاحية Encrypt/Decrypt على المفتاح المحدد، وتقييد الاتصالات الخارجية بمضيفين موثقين. لا تنشر نسخة Production دون بيئة staging منفصلة واختبار أذونات الخدمة.
- مراجعة privacy/logging: بيانات الهواتف والعناوين شديدة الخصوصية التشغيلية؛ لا تطبع طلباً كاملاً أو API token في السجلات. راجع النسخ الاحتياطي واستعادة البيانات وTTL/الاحتفاظ وحذف البيانات وفق اتفاق العميل والتشريعات ذات الصلة.

المراجع: https://firebase.google.com/docs/firestore/security/rules-conditions و https://firebase.google.com/docs/app-check/flutter/default-providers

## 3) عقود API لشركات التوصيل

- المحوّل Generic v1 يفترض `GET /health`, `POST /orders`, `GET /orders/{tracking}` وBearer token. **لا يعد تكاملاً مع أي شركة معيّنة**.
- قبل تفعيل شركة فعلية: وثائق Sandbox، أنواع المصادقة، الحقول الإلزامية، دلالات الدفع/التحصيل، طرق الإلغاء والاسترجاع، حد الطلبات، طريقة توقيع Webhook، المنطقة الزمنية، rate limits، قائمة رموز الحالات، idempotency وSLA.
- نفّذ اختباراً واقعياً لدورة: إنشاء → إرسال → استلام Tracking → تحديث قيد التوصيل → تم التسليم / مرتجع / ملغي، مع اختبار أحداث Webhook المكررة والخاطئة والمتأخرة.
- عند تعذر معرفة هل الشركة استلمت الطلب، لا تعِد الإرسال تلقائياً. أصبح لدينا `needs_review` ومسار تأكيد المدير العام بالمرجع والتتبع. **يجب تجربته مع المزود**؛ لا يكفي نجاح اختبار الوحدة.
- أرشفة الشركة توقف إرسال طلبات جديدة، وتواصل قبول تحديثات شحناتها القديمة ما دامت مفاتيح الربط متاحة.
- البحث الجديد يعتمد على `phoneDigits` و`customerKey`، ويستلزم تشغيل backfill للطلبات السابقة بعد نسخة احتياطية، وفحص الفهارس على Emulator/staging.

## 4) قوائم P0 قبل التسليم التجاري

- [ ] `flutter create` للمنصات المطلوبة في نطاق الاتفاق، ثم `flutter pub get`, `flutter analyze` بدون أخطاء و`flutter test` بلا فشل.
- [ ] واجهات الهاتف والتابلت والويب/اللابتوب بصور مقارنة، تفاعل كل زر ومقاسات 320/375/390/768/1024/1440/1920 وبـ 200% Text Scale.
- [ ] اختبارات Auth + صلاحيات المستخدمين الخمسة من الواجهة ومن وظائف الخادم المباشرة.
- [ ] تشغيل Emulator Suite لقواعد Firestore/Functions/Auth مع حالات الوصول الممنوع.
- [ ] Google OAuth إذا تقرر إدخاله في نطاق المشروع وتوثيق ربط UID آمن.
- [ ] مزود توصيل واحد حقيقي بإرسال/تتبع/إرجاع حالات + فقدان الاتصال والازدواج.
- [ ] عدادات دقيقة لكل تاريخ وحالة وفريق، بدلاً من حد 1000 الحالي، إذا كانت الأحجام المتوقعة تتجاوزه.
- [ ] إشعارات FCM (إذا اتفق على التنبيه الفوري خارج التطبيق) وتجربة Android/iOS؛ الإشعارات الداخلية وحدها لا تنتج صوتاً عند إغلاق التطبيق.
- [ ] مراقبة أخطاء Functions، تكاليف Firebase، تخزين مفاتيح KMS، نسخ احتياطي واختبار استعادة، خطط تراجع عن نشر فاشل.
- [ ] اختبار performance, throttling, pagination, retries, offline, auth-session renewal، واعتماد الترجمة العربية ومحدودية الأدوار.

**ممنوع وصف التطبيق بأنه منتج جاهز للنشر أو تسليمه لعميل على هذا الأساس قبل استكمال P0 وتوثيق الأدلة.**
