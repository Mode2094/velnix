# خطة التطوير خطوة بخطوة باستخدام Open Code

> يجب أولاً رفع مشروع UI الحالي أو فتح مساره. **أول بروموت سيكون للفحص وإخراج تقرير فقط**، دون أي تعديل أو كتابة للكود. بعد مراجعة التقرير، نبدأ بروموتاً تنفيذياً واحداً في كل خطوة، ولا ننتقل حتى يظهر تقرير تنفيذ ونتائج اختبارات وخلاصة الملفات المعدلة.

## مرحلة 0 — تقرير فحص فقط

- تحقق من بيئة Flutter/Dart ومن بنية الشاشات والاعتماديات.
- نفّذ `flutter create .` إذا لزم كإجراء لاحق **فقط بعد تقرير الفحص والموافقة**.
- حدد أخطاء compile أو lint أو RTL أو overflow والوظائف التجريبية فقط.
- صنف المخاطر في جدول (Critical/High/Medium/Low) وقدّم الملفات/الأسطر.
- لا تغير التصميم؛ لا تنفذ Firebase؛ لا تنشئ كوداً.

## مرحلة 1 — تصحيح الهيكل وتجهيز التشغيل

- توليد ملفات منصات التشغيل المطلوبة، فحص build، إصلاح التحليل والاختبارات.
- تجهيز Git، إعداد dev/test/prod flavors إذا كانت لها حاجة؛ تثبيت theme/widgets والنطاق.
- المخرجات: Build يعمل، tests نظيفة، تقرير واضح بدون توسيع ميزات.

## مرحلة 2 — فصل DemoStore إلى Architecture احترافية

- Interfaces للمستودعات، نماذج immutable وعناصر UI، State management (اختيار موحد يبرره التقرير)، DI وroute guards.
- ما زال يعمل في Mock mode؛ Snapshot/Widget tests تحفظ تصميم الشاشات.

## مرحلة 3 — Firebase Auth / RBAC

- تسجيل الدخول الحقيقي، إدارة العضويات والأدوار الخمسة، Security Rules وأمان خاص بالـtenant؛ اختبارات كل دور.
- حق إنشاء الطلب موجود لجميع الأدوار؛ المبيعات تشاهد إدخالات مدخلي البيانات فقط حسب الاتفاق.

## مرحلة 4 — أوامر الطلبات على Firestore

- إنشاء وعرض وتعديل وتصفية الطلبات، تحديث الحالة وفق قواعد workflow، عدم حذف الطلبات، Audit trail، optimistic UI بحذر وأخطاء واضحة.
- الربط بين بيانات المستخدم والطلب برقم معرّف ثابت، من دون الاعتماد على النص الظاهر.

## مرحلة 5 — شركات التوصيل وAPI الأولى

- اسم شركة التوصيل الحقيقية ووثائقها إلزاميان، ثم adapter للخادم، تجارب sandbox، إدارة بيانات الربط الآمنة، إنشاء الشحنة والتتبع.
- Webhook/ Polling، تحديث الحالات العكسي، Retry/Deduplication/Idempotency، mapping وتواريخ تغيير واضحة.

## مرحلة 6 — تقارير وإشعارات وتجويد

- بيانات اللوحة والتقارير الفعلية حسب صلاحيات المستخدم، إشعارات تشغيلية، الأداء والفلاتر والتحقق، Offline handling المناسب.

## مرحلة 7 — التسليم الفني

- اختبارات Android/iOS/Web حسب المتفق، Emulator suite، Build release، توثيق الإعداد والنشر الخادمي، تأكيد غياب الأسرار من الشيفرة، مراجعة أمنية وتسليم ضمن شروط الاتفاق.
- نشر التطبيقات في متاجر Google/Apple خارج نطاق السعر الأصلي.

## قواعد ثابتة لكل بروموت تنفيذ

1. اقرأ `README.md` وملفات `docs/` أولاً.
2. أرسل تقريراً قصيراً عن الوضع والخطوات والملفات التي ستُعدّل؛ التزم بالخطوة الحالية فقط.
3. لا تضف متجر/مخزون/محاسبة/اشتراكات ولا روابط شركات إضافية.
4. لا تحذف ملفات العمل أو تغير واجهاتنا جذرياً دون موافقة.
5. لا تخزن مفاتيح API على Flutter أو Firestore بصيغ مكشوفة؛ لا تستدع شركة التوصيل من التطبيق مباشرة.
6. نفّذ `flutter analyze` و`flutter test` وعمليات تحقق المرحلة إن أمكن، واذكر النتائج الحقيقية.
7. اختم بتقرير CHANGELOG + ملفات + اختبارات + مخاطر + خطوة تالية واحدة.
