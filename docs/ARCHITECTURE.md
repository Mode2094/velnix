# المعمارية
Flutter بواجهتين: live افتراضي يتطلب Firebase، وdemo صريح ببيانات محلية. Gateway يستدعي Functions؛ قواعد Firestore تمنع العميل من تعديل المستندات الحساسة، مع قراءة ملفه الشخصي لتحديث الجلسة.

الخادم يقرأ دور المستخدم النشط لكل طلب. نطاق مشرف المبيعات مشتق من أعضاء الفريق الحاليين. استعلامات createdBy تقسم مجموعات المالكين إلى 30، تدمج الصفحات بترتيب الوقت ومعرف المستند، وتحسب العدادات على النطاق نفسه. تغيير الفريق يحدّث authorizationVersion للمشرفين؛ لا يعيد كتابة تاريخ الطلبات. النظام مؤسسة واحدة؛ العزل متعدد المؤسسات غير مطبق.

الكتابة معاملات تعيد التحقق من الفاعل، وrevision للتعديل، ومعرف طلب ثابت لمنع التكرار. إرسال شركة التوصيل يسجل حالة إرسال قبل الشبكة؛ النتيجة غير المؤكدة تنتقل للمراجعة ولا يعاد إرسالها تلقائياً. أحداث الطلب تولد إشعارات داخلية دائمة. دفع FCM يستخدم pending/processing/sent/failed، أربع محاولات كحد أقصى وlease دقيقتين مع fencing ومجموعة أجهزة أُرسل لها بنجاح. استعادة العالق والمحاولات المؤجلة تستخدم جدول المزامنة الحالي كل 15 دقيقة، بلا Scheduler إضافي. لا يمكن ضمان exactly-once عبر FCM وFirestore إذا توقفت العملية بين الإرسال والحفظ؛ noticeId ثابت يتيح التعرف على التكرار. حالة القراءة مستقلة عن الدفع.

مفاتيح الشركات مشفرة عبر KMS. adapter generic_v1 مرجع بعقود واختبارات خادم HTTP محلي. webhook يحقق HMAC ثم يعالج الحدث بمعاملة ومنع تكرار؛ polling محدود وعادل. PDF يولد محلياً بعد جلب طلب حديث مخوّل.

إكمال داخلي: ready → delivered للمخوّل فقط دون companyId/hasDelivery/tracking/remoteStatus أو dispatchState محجوز، مع completionSource=internal والفاعل والوقت. التسليم من webhook يوسم carrier؛ الطلبات القديمة بلا مصدر لا يُختلق لها مصدر. directory.js يستعلم صفحات name ثم document ID بحجم 1..100، مع prefix search. الواجهات الإدارية تحمل 30 في الصفحة، والاختيارات تحمل كل الصفحات عند الحاجة.
